# HydraScript - User Guide

HydraScript is a visual 2D game engine that runs in your browser. You build games by placing objects in scenes and snapping logic blocks onto a grid. No code, no installs, no accounts. When your game works, you export it as a single HTML file that anyone can open and play.

This guide covers the editor. For every logic block, see the [Block Reference](block-reference.md).

## Start a project

Open `home.html`. This is the project hub: every project you have made, newest first. Click **New Project**, give it a name, and pick a starter template (or Blank). Templates are real working games, so open one, press Preview, and see how its logic is built before you change anything.

The featured template is **Hydra Quest**, a complete platformer built entirely with blocks: a main menu with best score, a how-to screen, a level select with locked levels, three platforming levels with coins, enemies, and a goal, a pause menu on every level, a win screen, and a game-over screen with retry. It is the best way to learn the engine, because every feature has a working example you can open in the Logic tab: level unlocks saved to the "HydraQuest" slot, the pause menu wired from the Game Paused condition, sprite animations on the hero, coins, and enemies, and a three-layer music loop built from On Timer blocks. Remix it: change the level layouts, add a fourth level, or reskin the hero.

Projects save to your browser automatically as you work. The hub can also import and export `.hydra` files, which are plain JSON you can share or back up.

You do not have to go back to the hub to do any of that: the editor header has the same three moves. **Export JSON** downloads the project you are editing as a `.hydra` file (it saves the current grid first, so the file matches what is on screen). **Import JSON** opens a `.hydra` file as a project in the editor; a file whose id already exists in your browser gets a fresh id instead of overwriting, and a broken file shows an error and leaves your current project untouched. **New** saves the current project, then opens a dialog with a name field and the full template list from the hub, so you can start a Blank Canvas or any starter template without leaving the editor.

The hub also works when your connection does not: if the styling service it normally loads over the network is unreachable, the hub falls back to a built-in local stylesheet, so the layout, dark theme, and project grid stay intact and you can keep opening projects. One visible difference in that mode: the small icon pictures come from a webfont, so without a connection they show as short words (like "add") instead of pictures. Buttons still work the same.

New here? Pick the **First Game Tutorial** template. It opens with a short guide pinned to the top of the editor: look at the scene (a player, a coin, and a score), open Logic to see the blocks that move the player and score the coin, then open Preview and play it with the arrow keys. The whole tour takes about five minutes. The guide stays until you click **Hide this guide**, and hiding it sticks for that project even after a reload. The tutorial game itself is ordinary blocks, so once you have played it, change it: make the coin worth 5 points, add a second coin, or swap the arrow keys for WASD and see the same blocks do the new thing.

## The editor has three tabs

**Scene / Entities** is where you build what the player sees. The canvas in the middle is your scene. The right-hand Inspector has panels:

- **Scenes**: add, rename, reorder, and switch between scenes (levels).
- **Hierarchy**: every object in the current scene, grouped by layer. Click to select.
- **World**: background color or image, world size, viewport size.
- **Create**: add sprites, text objects, and shapes.
- **Inspector**: edit the selected object (position, size, rotation, color, sprite image, physics, text). The top line names its kind, layer, and id, and the Visible and Locked checkboxes mirror the Hierarchy row.
- **Assets**: upload and manage images, audio files, and GIFs.

**Logic** is where you build what the game does: a 60 by 60 grid of blocks, HydraScript's signature scripting view.

**Preview** runs your game in the editor so you can test it. Restart restarts it.

**Compact panels:** the inspector and logic panels use a dense 12px type scale with tight spacing, so more controls fit on screen at once — the same information, less scrolling.

**Muted palette:** the editor's buttons, tabs, and highlights use softened, less saturated colors, so the workspace stays calm and the blocks on the logic grid stand out. The block colors themselves are unchanged — blue is still a condition, red is still an action — and the HydraScript logo keeps its violet-blue gradient.

**Resizable panels:** the Scene inspector and the Logic panel both have a drag handle on their left edge — the thin bar with a short grip in the middle. Drag it to trade stage space for panel space: wider when a property form needs room, narrower when the scene needs it. The widths stick: they are saved in your browser and restored the next time you open the editor. Double-click a handle (or focus it and press Home) to snap back to the default width, and focus it and use the Left and Right arrow keys to resize without a mouse (Shift steps further). On narrow screens the panels dock below their main area instead, so the handles hide there.

**Dockable panels:** each side panel can dock to the other edge of its tab instead of the right — the Scene inspector has a Dock button at the end of the scene toolbar, and the Logic panel has one next to the block search. Click it and the panel moves to the left, with the stage, the toolbar, and the resize handle moving with it, so the layout reads the same way, mirrored. Click it again to dock back on the right. The side sticks: it is saved in your browser and restored the next time you open the editor, and the resize handle moves with it, so a left-docked panel still drags wider and narrower from its right edge. On narrow screens the panels dock below their main area instead, so the side choice has no visible effect there.

**Compact blocks:** the Logic tab has a Compact blocks button next to the Dock button. Click it and the logic-grid cells shrink from 56px to 44px, with the block labels shrinking with them, so about a quarter more columns fit across the same stage — handy when a chain runs long or a fan-out runs wide. Click it again for the comfortable 56px cells. It changes nothing about the game: the grid is still 60 columns wide, the blocks and chains mean exactly the same thing in either density, and saved projects open the same way. The choice sticks: it is saved in your browser and restored the next time you open the editor.

**Hierarchy (the outliner):** the Scene tab's Hierarchy panel lists every object in the current scene under collapsible Layer groups, highest layer first, with a count per group. A collapsed group stays collapsed: the choice is saved in your browser and restored the next time you open the editor. Click a row to select its object. Every row has an eye and a lock: the eye hides the object — it leaves the stage and starts the game hidden, so use a Show Object block to reveal it later (a hidden object still exists for logic and still collides, like any invisible object). The lock stops the object being dragged on the canvas; clicking it still selects it, so it can always be inspected and unlocked. Double-click a name to rename it in place. Focus the list and the arrow keys move the selection from row to row (Home and End jump to the ends); Enter opens the Inspector for the selected object. While you search, the layer groups flatten away and the list shows exactly the matching rows. The Inspector mirrors the row toggles: its top line names the object's kind, layer, and id, and the Visible and Locked checkboxes do the same job as the eye and the lock.

## Objects

Every thing in a scene is an object: the player, enemies, coins, walls, score text. Select one to edit it in the Inspector.

- **Sprites** are rectangles with a color, or an image from your Assets. Set the image in the Inspector; the object keeps its size and the image fits inside it.
- **Text objects** show words on screen. Their content can be fixed or bound to a variable (see Logic).
- **Scene background**: set a color or a background image in the World panel.
- **Physics** (optional): turn on physics for gravity, friction, and bounciness. Static objects do not move but other things collide with them. Leave physics off for simple movement you control with blocks.

Objects have names. Logic blocks refer to objects by name, so give important objects clear names like `player`, `coin`, `enemy1`.

**Flip and scale.** The **Flip Object** action mirrors an object (flip horizontal when your character walks left, unflip when it walks right). **Set Scale** makes it look bigger or smaller (1 is normal, 2 is twice as big). Both change only how the object is drawn: the collision box keeps using the object's width and height, so use **Set Size** when the hitbox must change too. The **Position Check** condition can read an object's Scale X and Scale Y.

**Text manipulation.** Text objects can be restyled at runtime with ordinary blocks: **Set Text Size** (6 to 200), **Set Text Color**, **Set Text Style** (bold/italic on or off), and **Set Text Alignment** (left/center/right). These only affect text objects; every other kind is left alone. **Append Text** adds to the end of what a text object already shows, so an **On Timer** block plus **Append Text** builds a typewriter effect one letter per tick. The **Text Compare** condition checks what a text object currently shows (equals, does not equal, contains, starts with, ends with, is empty), handy for reacting when a score label reaches a value. And **Position Check** can read a text object's **Text length**.

**Picking one object out of many.** When several objects share a name (for example spawned enemies), the three **Pick** conditions in the Object category choose one of them for the blocks next to it: **Pick Nearest** picks the closest one to a Near object (leave Near object blank to measure from an X/Y point instead), **Pick Farthest** picks the furthest, **Pick Random** picks one at random. Place an action next to the pick with the same Object name and it applies only to the picked object — the block's Target picker already defaults to this. So **Pick Nearest** (Object: `enemy`, Near object: `player`) next to **Destroy Object** (Object: `enemy`) destroys only the closest enemy, which is how enemy AI targeting and homing pickups work. Pick Nearest and Pick Farthest re-evaluate every frame; Pick Random fires once per appearance (switch its trigger mode to "While true" for a fresh pick each frame).

**Layers and effects.** Every object has a draw layer (a number; higher draws on top). **Set Layer** writes an absolute number, while the four layer actions in the Object category manage relative order: **Bring to Front** puts the object above everything else, **Send to Back** drops it behind everything else, and **Move Up/Down a Layer** nudge it by a few steps — no need to remember numbers when cards shuffle or menus pop up. The **Layer Check** condition asks whether an object's layer matches a comparison ("is the card already above the table?"). Four more Object actions restyle how an object draws, without touching collision: **Set Blend Mode** (Normal, Add for glowing lasers and light rays, Multiply, Screen, Overlay, Difference), **Set Shadow** (color, blur, and offset for a drop shadow), **Set Visual Effect** (grayscale, sepia, invert, brighten, dim, soft blur — a grayscale flashback or a glitch moment), and **Clear Effects** to reset all three back to normal.

## Assets

Open the **Assets** panel in the Inspector. Upload images, audio files, and GIFs. Each asset shows a preview, its file size, and a usage badge: where it is used, or **Unused** if nothing references it (safe to delete).

- **Rename** changes the display name. **Replace** swaps the file while keeping every reference working. **Delete** asks first and clears the asset from any sprite or background that used it.
- Assign an image to a sprite or a scene background from their Inspector controls.
- Play an audio file with the **Play Sound** block (choose the file instead of the built-in tone).
- The storage summary shows how much space your assets use. If the browser runs out of space, the project still saves, minus the asset files, and tells you.

## Sprite animations

Select a sprite object and open the **Animations** section in the Inspector to make it move:

1. Click **+ Add animation**, give it a name (for example `Walk`), and pick a mode: **Loop** replays forever, **Ping-pong** bounces back and forth, **Play once** runs a single time.
2. Add frames from your uploaded images with **+ Add frame from Assets**. Reorder is not needed; frames play in the order listed. Use **Preview** to watch it before the game ever runs.
3. Optional: set **Play at start** so the animation is already running when the game begins.

Control animations from logic with four blocks: **Play Animation** (starts from the first frame), **Set Animation** (switches without restarting, handy for Walk to WalkHurt), **Stop Animation** (back to the static sprite), and **Animation Finished** (fires when a play-once animation completes — chain attacks, cutscenes, or respawns off it). Everything works the same in the preview and in exported games.

## Animation state machines

When a character has several moods — idle, running, jumping, hurt — a state machine keeps them organized. Select a sprite object and open the **Animation States** section in the Inspector (right under Animations):

1. Click **+ Add state** and name the moment (for example `Run`).
2. Pick which animation the state plays and a **Speed** multiplier (1.25 makes the run cycle snappier without re-editing frames). A state with no animation is a pure logic flag.
3. Optional: set an **Initial state** so the game starts in it (it wins over Play at start when both are set).

States are data; transitions stay in your logic grid with two blocks: **Set Animation State** (enters the state — its animation starts automatically) and **Animation State** (true while the object is in that state, invertible). A platformer hero looks like this:

- Every Frame, Action Held "right" -> Set Animation State "Run"
- Every Frame, NOT Action Held "right" -> Set Animation State "Idle"
- Animation State "Run", Just pressed "space" -> Set Animation State "Jump"

Renaming an animation repoints every state bound to it, and renaming a state repoints every block using it, so nothing orphans silently. Anything a state machine does can be rebuilt by hand from Play Animation blocks — the machine is an organizer, never a cage. Everything works the same in the preview and in exported games.

## Blend spaces

A blend space mixes a character's animations by two values, X and Y — the classic top-down or twin-stick setup. Select a sprite object and open the **Blend Spaces** section in the Inspector (right under Animation States):

1. Click **+ Add blend space** and name the mix (for example `Move`). Set its **Speed (fps)** — all points share one frame clock, so the walk cycle never restarts when the direction changes.
2. Click **+ Add direction** for each animation and place it at an X/Y point: `Idle` at 0,0, `Walk Right` at 1,0, `Walk Left` at -1,0, `Walk Up` at 0,-1, `Walk Down` at 0,1.

Then drive it from the logic grid with the **Set Blend** block — X and Y are expressions, so this is a one-block recipe:

- Every Frame -> Set Blend "Move", X = Action Input "moveX", Y = Action Input "moveY"

Standing still plays Idle; moving right plays Walk Right; moving diagonally crossfades the two nearest frames (the runner-up draws at partial alpha over the winner — a plain crossfade, no shader work). The **Stop Blend** block turns the blend off (the object goes back to its normal animation; leave Blend empty to stop whichever is active), and the **Blend Active** condition reads whether a blend is on — it evaluates every frame like a variable read, even while paused.

Honest limits: only one blend space is active per object at a time, blend spaces always loop (use Play Animation for one-shots), and weights are distance-based, so points placed far apart blend less. Renaming an animation repoints every blend point bound to it, and deleting an animation unbinds it. Anything a blend space does can be rebuilt by hand from Play Animation blocks with direction checks — the blend is an organizer, never a cage. Everything works the same in the preview and in exported games.

## 2D lighting and shadows

2D scenes start fully lit — fine for building, flat for atmosphere. For mood, give the scene **Darkness** and add lights. In Scene Settings (in a 2D scene) the **Darkness** slider dims the whole scene: 0 is day, 100 is pitch black, and the **Darkness tint** picks the color of the dark (black for night, deep blue for underwater, dark red for a cave). The darkness overlay draws above the world and below the HUD, so menus stay readable in the dark.

**Lights** punch soft round holes in the darkness. Place a **Light** object from the Create palette (the bulb button — in a 2D scene it creates a 2D light; in a 3D scene it creates a 3D light instead). A light is invisible in the game: in the scene editor it shows as a bulb glyph tinted by its color, so you can drag it into place, but Preview and exported games never draw it — it only erases darkness around itself. Any object can also be a light: select a sprite and check **Emit light** in the Inspector's **Lighting** section, so a torch sprite both draws and shines. Per light you set **Light radius** (how far it reaches), **Light color** (a soft tint inside the pool — white is a plain light, orange is a torch), and **Light intensity** (1 is a full hole, 0.5 is a dim pool).

**Shadows** come from the **Cast shadow** checkbox in the same Lighting section. A cast-shadow object blocks the light: a simple shadow shape stretches away from the light behind it — put a wall between the torch and the floor and the floor goes dark behind the wall. This is the silhouette-extrusion trick, not real raycast shadows: it is cheap and looks right for top-down and side-view games.

**Changing lighting while the game runs** is three blocks in the **Lighting** palette category:

- **Set Darkness** fades the scene: `Every Frame` → Set Darkness `0.5 + 0.5 * Math.sin(time * 0.1)` is a slow day/night pulse; one block with 0.9 is instant night.
- **Set Light** moves, recolors, or switches a light: `Every Frame` → Set Light (`Torch`, Radius `200 + Math.random() * 30`) is a flickering torch; Set Light (`Lamp`, Off) kills a lamp when the player flips a switch.
- **Darkness Level** reads the current darkness for gameplay: Darkness Level `>= 0.7` → spawn bats is the night-behavior gate. It evaluates every frame like a variable read, even while paused.

A few honest limits: shadows use the object's unrotated bounds (rotation is ignored), light color is a soft tint rather than a true colored-light model, HUD widgets draw above the darkness and never emit light, and hidden objects do not shine (switch a light off with Set Light instead of hiding it). Darkness 0 skips the overlay entirely, so old projects render exactly as before. Everything works the same in the preview and in exported games.

## Physics joints

Joints link two objects so they move together: a lantern swinging from a ceiling, a trailer towed behind a truck, a bungee cord, a wrecking ball on a chain. A joint lives on the scene and links two objects by name, and the solver runs every frame in the preview and in exported games, after collisions, so joints and walls agree. Three kinds, each one plain sentence:

- **Distance** is a rigid rod: the two centers stay exactly the length apart. Length 0 welds the centers together.
- **Rope** is a chain: the centers may come closer freely, but never stretch past the length. A hanging lantern is a rope from a static ceiling anchor to the lantern.
- **Spring** is a stretchy cord: it pulls both ends toward the rest length, damped so it settles instead of bouncing forever. Stiffness (0 to 1, default 0.05) sets how hard it pulls.

The no-blocks way in is the Inspector **Joints** section on any 2D physics object: pick the other object, the type, a length (leave it blank to use the distance they are apart right now), and a stiffness for springs, then **+ Add joint**. (Joints link objects by name, so name the object first — a fresh sprite starts unnamed, and the section says so.) Static objects act as anchors that never move — a rope from a static anchor is how a swing hangs. The same three blocks in the **Physics** palette category do it at runtime:

- **Create Joint** links two objects (leave Length blank for their current distance; re-creating the same pair and type replaces the old joint, so a rod and a spring on the same pair can coexist).
- **Remove Joint** unlinks two objects (leave Object B blank to remove every joint involving Object A).
- **Joint Connected** reads whether a joint links two objects (either direction; leave Object B blank to test whether Object A has any joint). It evaluates every frame like a variable read, even while paused.

A few honest limits: joints connect object centers, with no anchor offsets and no rotation or angular physics, so a "hinge" here holds centers together rather than swinging a body around a pivot; joints ignore collision layers (a joint holds even across layers); joints are 2D only (3D objects never solve). A joint whose endpoint is missing, hidden, or destroyed simply does nothing that frame instead of breaking the game. Anything a joint does can be rebuilt by hand from position and velocity blocks — the joint is an organizer, never a cage. Everything works the same in the preview and in exported games.

## Skeletal animation

Sprite animations redraw a whole character every frame. Skeletal animation moves a character's parts instead: give an object a **bone rig** — a small tree of named bones — and animate it with a few angle numbers per bone. A walk cycle is four numbers on a leg bone, not four redrawn sprites.

The no-blocks way in is the Inspector **Skeleton** section on any sprite-drawn object. **+ Add bone** makes a bone: a name, a parent (Root starts at the object center; any other bone hangs off its parent's tip, so turning a shoulder swings the whole arm), a length, a base angle, a thickness, a color, and optionally an image. Angles are degrees: 0 points right, 90 points down, like object rotation. A bone with no image draws as a thick limb line in its color; a bone image stretches along the bone, so draw limb art as a horizontal strip. A bone with length 0 is a pivot — it draws only a joint dot, and its children hang off it. The section shows a mini preview of the rest pose, so you can see the rig as you build it. **Hide sprite, draw bones only** skips the sprite and draws just the rig, for a pure stick figure.

**+ Add animation** makes a keyframed animation: a name, a speed in fps, a mode, and one angle list per bone (**+ Add track** picks the bone and its angles, comma-separated, like `0, 40, 0, -40`). Modes are Loop (wraps), Ping-pong (bounces between the first and last frame), and Once (holds the last frame when it finishes). Tracks shorter than the animation wrap at their own length, and the animation's frame count is its longest track. Bones draw over the sprite in Preview and exported games, so a body sprite plus articulated arms and legs just works.

The four blocks in the **Skeleton** palette category drive the same rig at runtime:

- **Play Skeleton Animation** plays one of the object's animations. Re-playing the same animation keeps its clock, so playing it every frame does not restart the cycle; unknown names warn and hold.
- **Stop Skeleton Animation** stops the animation (leave Animation blank to stop whichever is active). The pose returns to the base angles, plus any hand poses.
- **Set Bone Angle** poses one bone by hand, in degrees. A posed bone wins over a playing track until a new skeletal animation starts — a walk cycle plus a hand-aimed arm is one block per frame (`Every Frame` → Set Bone Angle (`arm`, `Math.atan2(...)` style aiming, or a sine wave for waving).
- **Skeleton Playing** reads whether an animation is playing (a finished once-run reads false — its pose holds, its playing stops). It evaluates every frame like a variable read, even while paused.

A few honest limits: bones are 2D only and carry no collision (the object keeps its normal box or circle collider), bone images stretch to the bone's length and thickness rather than keeping aspect ratio, and there is no inverse kinematics — you pose angles directly. Anything a skeletal animation does can be rebuilt by hand from rotation and position blocks — the rig is an organizer, never a cage. Everything works the same in the preview and in exported games.

## Localization

One string table translates the whole game. Open the **Localization** tab: pick a **Default language** (usually `en`), add languages with the plus button (`es`, `fr`, whatever codes you want), then add strings with the font button. Each string has a key like `play_button` and one line of text per language. Leave a language blank and the game falls back to the default language's text for that key.

There are two ways to use a key, and they cover every label in a game:

- **Bind a text object to a key.** Select any text object and set its **Localization key** in the Inspector. From then on, the label shows the key's translation instead of its authored text, in the preview and in exported games. This is the way to translate a menu: bind every label once, and switching languages updates all of them.
- **Read a key with a block.** **Set Text from Key** writes a key's translation into a text object on demand (for dialog lines that change mid-game), and **Set Variable from Key** copies a translation into a game variable so it can feed Set Text or any other block.

**Set Language** switches the whole game at runtime: a language-select menu is one block per button (`Object Clicked` on the Spanish flag button → Set Language `es`), and every bound label follows at once. **Language Is** reads the current language for logic that only applies in one language, like showing a language-specific help card. It evaluates every frame like a variable read, even while paused.

A few honest limits: keys match exactly, with no plurals, gender forms, or placeholders inside the text (compose those with Set Text and variables); language codes are free-form strings you define, with no built-in locale list and no automatic browser-language detection (Set Language is the explicit switch); and translations are plain text. The current language is a per-run setting: it starts at the project's default language, survives scene switches inside a run, and resets on the next run. Anything localization does can be rebuilt by hand from Set Text blocks. The table is an organizer, never a cage. Everything works the same in the preview and in exported games.

## Dialogue

Conversations a beginner can actually write. Open the **Dialogues** tab and add a dialogue with the plus button: name it (for example `Guard intro`), then write its lines — one row per line, with who speaks and what they say. A line can offer choices: click **+ Choice** on a line, write the choice's label (for example `Show the pass`), and pick which line that choice jumps to (**End dialogue** when the choice ends the conversation). Renaming a dialogue repoints every Start Dialogue block that used the old name.

To play a conversation, build a dialogue box from ordinary objects first: a panel for the box, one text object for the speaker's name, one for the line itself (hide the whole panel until the conversation starts). Then three kinds of blocks do the work:

- **Start Dialogue** picks the conversation and the two text objects it appears in, plus a typing speed in characters per second (40 is the default; 0 shows the whole line at once). The speaker name and the line appear in those objects, revealed letter by letter. Starting a dialogue that is already running restarts it from the first line.
- **Advance Dialogue** moves the conversation one step: it finishes the current line's typing first, then goes to the next line (past the last line it ends). It stays quiet on a choice line — the player has to pick. Wire it to a key or a Next button (`Key Just Pressed` → Advance Dialogue, or `Object Clicked` on the Next button → Advance Dialogue).
- **Choose Dialogue Option** picks the numbered choice while the dialogue is waiting (1 is the first), jumping to the line that choice points at. Build the choice buttons yourself: one button + text label per option, **Set Choice Text** writes each choice's label into its label (run it while the dialogue waits), **Dialogue Choice Available** gates each button so a two-choice conversation never shows a third empty button, and `Object Clicked` on a button → Choose Dialogue Option with that button's number.

**Dialogue Active** is true while any dialogue is running — show the panel when it turns true, hide it when it turns false (inverted). **Dialogue Waiting For Choice** is true while a choice line is fully revealed and waiting — show the choice buttons then, and hide the Next button. **Stop Dialogue** ends a conversation at once. All three conditions are state reads: they evaluate every frame, even while paused, and the typewriter keeps revealing while the game is paused (dialogue is UI; the world is frozen).

A few honest limits: lines are plain text, with no rich text or placeholders inside the text (compose those with Set Text and variables); choices jump by line number, with no named labels or sub-dialogue calls; there is one running dialogue at a time (starting another restarts from the first line); and the typewriter has one speed per Start Dialogue block, with no per-character sound. When a dialogue ends, the speaker and text labels keep the last line that was showing — hide the panel with Dialogue Active (inverted) if you want it to disappear. A scene switch ends a running dialogue, so a fresh scene never inherits a half-finished conversation. Everything works the same in the preview and in exported games.

## Inventory

The backpack the player carries. Open the **Items** tab and add an item with the plus button: name it (for example `Brass key`), set its **Max stack** (how many fit in the backpack at once; 1 makes a unique item, so a second key can never sneak in), and write a short description so you remember what it is for. Renaming an item repoints every item block that used the old name.

Five action blocks work the backpack:

- **Add Item** puts the count of the named item in (up to its max stack). A chest is just `Object Clicked` on the chest → Add Item `Gold coin` 5.
- **Remove Item** takes up to the count out (taking more than is carried takes what is there, and the entry drops at 0). Drinking a potion is Add Item in reverse: Remove Item `Potion` 1.
- **Set Item Count** sets the count outright, clamped to 0 up to the max stack (0 drops the entry). Use it to hand the player an exact amount, or to restore a saved count after Load Game.
- **Read Item Count** copies how many of the named item is carried into a game variable, so you can show the count in a label, compare it, or save it. A defined item with nothing carried reads 0.
- **Clear Inventory** empties the whole backpack at once — a new game, a fresh level, or a "lose everything" trap.

Two conditions read it, and both are state reads that evaluate every frame, even while paused:

- **Has Item** is true while the backpack holds at least the count (1 by default). Gate a locked door on Has Item `Brass key`, or a shop on Has Item `Gold coin` 10.
- **Item Count** compares the carried count against a value you enter (at least, at most, exactly, and the rest), for thresholds Has Item cannot express — a shop that only shows its rare stock at 10 coins, or a quest that completes at 8 gems. An item never held reads as 0.

Counts can be expressions, so a variable can feed them: Add Item `Gold coin` with the count `reward` adds whatever the reward variable holds. Counts are whole numbers — fractions round down.

A few honest limits: there is one backpack per run, and it survives scene switches inside a run (like the current language) but resets on a fresh run; there is no built-in inventory HUD, so show counts by reading them into a text object with Read Item Count and Set Text; descriptions live on the item definition, not on each carried copy; and the backpack does not travel inside save slots (slots store game variables only). To persist it, read each count into a variable with Read Item Count before Save Game, and restore it with Set Item Count from that variable after Load Game — the same blocks you already use, no special save step. Everything works the same in the preview and in exported games.

## Quests

The objectives the player works through. Open the **Quests** tab and add a quest with the plus button: name it (for example `Collect 4 coins`), set its **Target** (how much progress finishes the quest; 1 makes a one-shot quest, like reaching the goal or talking to the guard), and write a short description so you remember what it is for. Renaming a quest repoints every quest block that used the old name.

Six action blocks work the quest log:

- **Add Quest Progress** adds the amount to the named quest, up to its target — reaching the target completes it. A coin is just `Object Clicked` or a collision → Add Quest Progress `Collect 4 coins` 1.
- **Set Quest Progress** sets the progress outright, clamped to 0 up to the target (0 drops the entry). Reaching the target completes the quest; setting it back below un-completes it, a deliberate manual override. Use it to hand the player an exact amount, or to restore a saved count after Load Game.
- **Complete Quest** completes the named quest at once: progress fills to its target. A cutscene that finishes a quest, or a cheat code, is one block.
- **Reset Quest** drops the named quest's progress and done flag, so it reads as never started — a replayable quest, or a fresh attempt after a failed run.
- **Read Quest Progress** copies the named quest's progress into a game variable, so you can show the count in a label, compare it, or save it. A defined quest with no progress yet reads 0.
- **Clear Quests** empties the whole quest log at once — a new game, or a "start over" button.

Two conditions read it, and both are state reads that evaluate every frame, even while paused:

- **Quest Complete** is true while the named quest is complete. Gate a reward on it: Quest Complete `Collect 4 coins` (edge trigger) → Add Item `Brass key` 1, or open the exit door.
- **Quest Progress** compares the quest's progress against a value you enter (at least, at most, exactly, and the rest), for thresholds Quest Complete cannot express — a hint that only shows at 2 of 3 enemies defeated, or a warning at 0. A quest never started reads as 0.

Amounts can be expressions, so a variable can feed them: Add Quest Progress `Defeat 3 enemies` with the amount `bonus` adds whatever the bonus variable holds. Progress is whole numbers — fractions round down.

A few honest limits: there is one quest log per run, and it survives scene switches inside a run (like the backpack) but resets on a fresh run; there is no built-in quest HUD, so show progress by reading it into a text object with Read Quest Progress and Set Text; descriptions live on the quest definition, not on the carried copy; and a quest has one target and one done flag, with no multi-step chains — chain quests by gating the next quest's progress on the previous quest's Quest Complete. The log does not travel inside save slots (slots store game variables only). To persist it, read each progress into a variable with Read Quest Progress before Save Game, and restore it with Set Quest Progress from that variable after Load Game — the same blocks you already use, no special save step. Everything works the same in the preview and in exported games.

## Achievements

The permanent trophies the player earns. Open the **Achievements** tab and add an achievement with the plus button: name it (for example `Coin hoarder`) and write a short description of what earns it, so you remember what it is for. Renaming an achievement repoints every achievement block that used the old name.

Achievements are the companion to quests, with one deliberate difference: a quest is a per-run objective that resets on a fresh run, while an achievement is permanent. Once unlocked, it stays unlocked across runs, scenes, and restarts — until Lock Achievement or Reset Achievements takes it back. That makes achievements the meta-progression: beat every level, collect 100 coins across any number of runs, finish a level without dying.

Four action blocks work the unlocked set:

- **Unlock Achievement** unlocks the named achievement for good. A quest finishing is the usual trigger: Quest Complete `Collect 4 coins` (edge trigger) → Unlock Achievement `Coin hoarder`. Unlocking one that is already unlocked changes nothing.
- **Lock Achievement** locks the named achievement again, so it reads as never earned — a "reset this trophy" option, or a way to test an unlock flow from scratch.
- **Reset Achievements** locks every achievement at once — a "reset progress" menu, or a clean slate for testing.
- **Read Achievement Count** copies how many achievements are unlocked into a game variable, so you can show the count in a label or save it.

Two conditions read it, and both are state reads that evaluate every frame, even while paused:

- **Achievement Unlocked** is true while the named achievement is unlocked. Put it on edge trigger to fire once, exactly when the trophy is earned: show the badge, play the fanfare.
- **Achievement Count** compares the number of unlocked achievements against a value you enter (at least, at most, exactly, and the rest) — a veteran badge at 3 trophies, a secret door when every achievement is unlocked.

A few honest limits: there is no built-in achievement toast or HUD, so show an unlock by gating a text object on Achievement Unlocked; descriptions live on the achievement definition, not on the carried copy; and an achievement has no progress counter of its own — count progress with a quest or a variable, then unlock when it completes. The unlocked set is stored per game (one entry per project), so the preview and exported games share the same trophy case the way save slots share their keys, and renaming the project keeps it — copying the project to a new id starts it fresh. Everything works the same in the preview and in exported games.

## Cutscenes

The scripted scenes the game plays by itself: an intro before Level 1, a transition between levels, an ending after the final boss. Open the **Cutscenes** tab and add a cutscene with the plus button: name it (for example `Intro`) and write a short description of what it is for, so you remember. Then add steps with the **Step** button — each step is one beat, and the engine plays them in order, top to bottom. Renaming a cutscene repoints every cutscene block that used the old name.

Five kinds of step:

- **Wait** holds for the seconds you enter — a beat of silence, a pause for effect.
- **Show text** writes text into a text object (a caption, a line of narration) at the step start and holds it for the seconds you enter. The text stays after the step ends; the cutscene never blanks it, so clear it yourself with a Set Text block if the next scene should not show it.
- **Move object** glides an object from wherever it is to the X/Y you enter, over the seconds you enter — a character walking off, a backdrop panning across. Zero seconds teleports the object to its target at once.
- **Play sound** plays a named sound asset once. The step ends at once, so a sound never blocks the timeline — put it next to a Wait if the music should finish before the next beat.
- **Switch scene** switches to the scene you pick. The step ends at once, and the cutscene keeps playing in the new scene, so one cutscene can carry the player across a level change.

Four blocks drive cutscenes:

- **Play Cutscene** starts the named cutscene from its first step, replacing any cutscene already playing. The usual trigger is Game Start: Game Start → Play Cutscene `Intro`.
- **Stop Cutscene** stops the running cutscene — a skip button. Stopping counts as finished, so the Cutscene Finished hook runs just as it would at a natural ending. Leave the name blank to stop whichever cutscene is playing; a name stops only that one.
- **Cutscene Playing** is true while the named cutscene is playing (leave the name blank to mean any cutscene) — the gate for hiding the HUD and locking player input while a scene plays. It is a state read that evaluates every frame, even while paused.
- **Cutscene Finished** is true once the named cutscene has finished (leave the name blank to mean whichever cutscene finished most recently). Put it on edge trigger to fire once, exactly when the scene ends — the switch-to-Level-1 hook. A natural ending or a stop both count, so a skip button lands in the same place.

A cutscene freezes while the game is paused (it moves the world, so the pause freeze applies), and it survives scene switches inside a run, resetting only on a fresh run. A few honest limits: steps are a fixed list, not a track editor — there is no scrubbing, no parallel tracks, and no per-step easing (a move is a straight linear glide; chain moves, or use a tween, for curves); one cutscene plays at a time; a cutscene has no progress counter of its own — gate on Cutscene Finished, or drive a variable from the steps themselves; and the runtime does not travel inside save slots, so replay the cutscene after Load Game, or skip it with a Cutscene Finished gate. A step whose target is missing (an object, sound, or scene that does not exist — including one renamed after the step was written) warns once and the timeline moves on, so a typo never stalls the show. Everything works the same in the preview and in exported games.

## High Scores

The ranked leaderboard the game keeps for itself: the best scores, best first, kept across runs, scenes, and restarts. Open the **High Scores** tab and set the table size (how many entries the board holds, 1 to 50, 10 by default) and the default name — the name a score gets when it is submitted without one. The tab also shows the scores stored for this game, best first, so you can see the board fill up as you test.

Three action blocks work the table:

- **Submit Score** submits a score (a number or an expression, so a variable can feed it — Submit Score `score`) with a name. Leave the name blank to use the default name from the tab. The usual trigger is the end of a run: Game Over → Submit Score `score` `Alex`. A score that does not beat the lowest entry on a full table changes nothing, and a tie with the lowest entry does not displace it — the first player to reach a score keeps the higher rank.
- **Read High Score** copies the score at the rank you enter (1 is the best) into a game variable, and its name into a second variable, so you can show the board in labels: Game Start → Read High Score rank 1 into `topScore` and `topName`, then Set Text on a label to `topName` and `topScore`. A rank past the end of the table writes nothing, so a fresh game with no scores leaves your variables alone; leave a variable blank to skip it.
- **Clear High Scores** empties the whole board at once — a "reset progress" menu, or a clean slate for testing. The tab's **Clear stored scores** button does the same thing from the editor, including clearing a running preview's table.

Two conditions read it, and both are state reads that evaluate every frame, even while paused:

- **Is High Score** is true while the score you enter would make the board — the table has room, or the score beats its lowest entry. Put it on edge trigger to fire once, exactly when a run ends with a board-worthy score: Game Over → Is High Score `score` (edge) → Show "New best!". A non-numeric score never qualifies.
- **High Score Count** compares the number of scores on the board against a value you enter (at least, at most, exactly, and the rest) — a "leaderboard full" badge at 10 entries, or a first-score-ever hint when the count is 0.

A few honest limits: there is no built-in leaderboard HUD, so show the board by reading ranks into variables with Read High Score and writing them into text objects with Set Text; the table holds scores, not replays or per-level splits — keep one table per game, or submit a combined score; Submit Score does not report the rank it earned back into a variable, so read the rank you care about with Read High Score instead; and the table is stored per game (one entry per project), so the preview and exported games share the same board the way save slots share their keys, and renaming the project keeps it — copying the project to a new id starts it fresh. The table does not travel inside save slots (slots store game variables only). Everything works the same in the preview and in exported games.

## Time scale

One number says how fast the game world runs: 1 is normal speed, 0.3 is slow motion, 0.5 is half speed, 2 is double speed, and 0 freezes the world outright. Three action blocks and one condition, all in the **Time** category:

- **Set Time Scale** sets the speed (a number or an expression, so a variable can feed it). The usual trigger is drama: Player dies → Set Time Scale `0.3`, then a timer brings up the Game Over screen — the fall plays out in slow motion. A non-numeric scale warns and holds, and any other value clamps to 0..4.
- **Reset Time Scale** is back to normal speed at once — the un-freeze button for a slow-motion death or a frozen world. Put it on the retry key: Key Just Pressed (R) → Reset Time Scale, Restart Scene.
- **Read Time Scale** copies the current scale into a game variable, so you can show it in a label or save it. Leave the variable blank to skip it.
- **Time Scale** is true while the current scale compares against the value you enter — a "SLOW-MO" badge while the scale is under 1, or a speed-up indicator while it is over 1. It is a state read that evaluates every frame, even while paused.

The scale slows everything that advances on the frame step — physics, sprite animations, tweens, particles, cutscenes, dialogue typing, and the named timers — together, the way Unity's Time.timeScale does. A 3-second timer takes 6 real seconds at half speed and 1.5 real seconds at double speed. Scripts, input, and buttons keep running at full speed whatever the scale is, so a slow-motion death can always end in a "press R to retry" block, and a freeze at scale 0 is never a dead end. The profiler's FPS stays honest too, since it reads real timestamps.

The scale is run-level state: it survives scene switches inside a run, like the language, and resets only on a fresh run. It never travels in save slots (slots store game variables only — read the scale into a variable first if a save must remember it).

A few honest limits: there is no script-API surface yet — use the blocks; there is no smooth ramp, the scale changes at once (ramp it yourself with repeated Set Time Scale, e.g. every frame toward the target); and dialogue typing slows with the world, including while paused, because the typewriter reads the same scaled step. Everything works the same in the preview and in exported games.

## Scene Transitions

Scene changes do not have to be instant cuts. The **Transition to Scene** block fades the screen to black (or sweeps a black panel across it), switches scenes under full cover, and fades back in on the new scene — so level changes, menu entries, and game-over returns feel finished instead of abrupt. Two action blocks and two conditions, all in the **Scene** category:

- **Transition to Scene** switches to the scene you pick, with an effect and a duration. The default effect (Fade to black) and total duration (0.5 seconds) come from the **Transitions** tab; the block can override both for one switch, or leave them on Default. The duration is the total time: half to fade out, half to fade back in. Leave Duration blank to use the default, and set it to 0 to switch at once. An unknown scene warns and holds, so a typo never leaves the game stuck on black.
- **Cancel Transition** stops a transition that is playing — a skip button for a long fade. Cancelling while the screen is fading out stays in the current scene; cancelling while it is fading back in finishes at once, since the scene already switched.
- **Transition Playing** is true while a transition is running — hide the HUD while moving to the next level, or freeze player input until the new scene is fully in. Leave the Scene blank for any transition, or pick one to gate only on the way to that scene. It is a state read that evaluates every frame, even while paused.
- **Transition Finished** fires once, exactly when a transition ends (an instant switch counts too) — show the "Level 2" banner only after arriving there: Transition Finished "Level 2" (edge) → Show banner. Leave the Scene blank for any transition, or pick one to run what happens next only after arriving at that scene.

Starting a transition replaces one already playing, and the plain **Switch Scene** block stays an instant cut — transitions are the deliberate on-ramp, never a change to what already worked. The transition is run-level state: it survives the scene switch it performs, and resets only on a fresh run. It never travels in save slots (slots store game variables only).

A few honest limits: there is one transition at a time, and only the two effects (Fade to black, Wipe across) — the overlay is always black, with no custom colors and no per-effect easing (a wipe is a straight linear sweep); and the transition follows the time scale like a cutscene does, because both runtimes feed it the scaled frame step — a fade at half speed takes twice as long. Everything works the same in the preview and in exported games.

## Tweening

Tweens animate one numeric property of an object over time with an easing curve — the quick way to add "juice": pickups that pop, enemies that shake when hit, menus that fade in. Drop a **Tween** block and pick a preset (Move right 100, Fade out, Spin 360 degrees, Shake...), or set it up yourself: choose the property (X/Y position, width, height, rotation, opacity), a target value (a number or an expression like `hero.posX + 200`), a duration in seconds, and an easing (Ease out for snappy UI, Bounce for balls, Pop for pickups). Turn on **Relative** to add the target to the starting value — perfect for jumps and moves.

A tween that is set to **Once** fires **Tween Finished** when it completes (chain a respawn or a cutscene off it); **Loop** and **Ping-pong** run forever. A new Tween on a property replaces any tween already running on it, and **Stop Tween** freezes the property where it is. Everything works the same in the preview and in exported games.

## Particles

Particles are the quick way to add juice: explosions, sparkles, smoke, confetti, rain, fire, magic trails. They live in the **Particles** palette category as four blocks:

- **Emit Burst** — a one-shot burst. Pick a preset (Explosion, Sparkle, Smoke puff, Confetti, Splash) or set it up yourself: X and Y (expressions, so `hero.posX, hero.posY` works), count, speed, spread, direction (0 = right, 90 = down, 270 = up), lifetime, start/end size, start/end color, gravity (negative makes particles rise, great for smoke), shape (circle or square), and an additive-glow toggle for fiery glows.
- **Start Emitter** — a continuous emitter with a rate (particles per second) instead of a count. Give it a name like `fire` or `rain`. Set **Follow object** to make it track something — a rocket trail is just Game Start → Start Emitter "trail" following the player.
- **Stop Emitter** — stops an emitter by name (blank stops all of them). Particles already flying finish their lifetimes.
- **Clear Particles** — removes live particles instantly, one emitter's or everything.

Two details worth knowing: every particle fades out as it dies, and speed and lifetime vary a little per particle so bursts look natural without extra work. Particles are world-space, so they scroll with the camera, and they freeze while the game is paused. Starting an emitter with a name that is already running replaces it, so you never get double spawns by accident. A new scene starts with a clean slate. Everything works the same in the preview and in exported games.

## Action-based input

Real engines never read raw keys in game logic. They read named actions, and HydraScript works the same way. Open the **Inputs** tab and define actions like `Jump`, `Move Left`, or `Shoot`. Each action binds up to two keyboard keys, one gamepad button, and one touch zone. Then use the **Action Input** condition block with the action's name instead of a key block. The same logic now responds to keyboard, gamepad, and touchscreen with no extra blocks: a player pressing Space, tapping gamepad button A, or touching the screen's left half all fire `Jump`.

Three details that make this practical:

- **Touch zones** are screen halves: left, right, top, bottom. A finger sits in one horizontal and one vertical zone, so two fingers can drive two actions at once. A common setup: left half moves left, right half moves right, and a HUD button object calls the jump action through its own logic.
- **The wand button** in the Inputs tab adds a ready-made platformer set (Move Left, Move Right, Jump, Shoot, Interact) with sensible keyboard, gamepad, and touch bindings. Start from that and tweak.
- **Players can remap.** The **Remap Action** block changes an action's key binding while the game runs, so a settings screen is plain blocks: a button per action, a "press a key" prompt, then Remap Action. **Reset Action Bindings** restores the defaults from the Inputs tab.

Like raw key input, actions keep working while the game is paused, so pause menus can use them. Everything works the same in the preview and in exported games.

For everything the named actions don't cover, the **Input** category has seven raw input conditions. They read the live input state directly, no Inputs tab setup needed:

- **Cursor Position** — compare the mouse cursor's X or Y (screen pixels) against a value. Cursor zones, screen-edge checks, aim-like logic without an object.
- **Any Key Pressed** — true while any keyboard key is held down. Invert it for "no key is pressed" ("press any key to start", attract-mode timers).
- **Touch Active** — true while at least one finger is touching the game. Invert it for "no finger is down".
- **Touch Count** — compare the number of fingers touching the game against a value. Use 2 for two-finger gestures.
- **Gamepad Connected** — true when at least one gamepad is connected. Browsers ask the player for permission the first time a game reads a gamepad, so this usually fires after the player presses a button once.
- **Gamepad Button** — read one of the 16 standard gamepad buttons directly: Held, Just pressed, or Released. For the shared keyboard/gamepad/touch path, prefer Action Input with a named action.
- **Gamepad Stick** — compare an analog stick axis (left/right, X/Y, -1 to 1) against a value. The default 0.2 ignores stick drift.

All seven are state reads: they evaluate every frame and keep working while the game is paused. Held (and all the position/count/connection reads) fire every frame while true; Just pressed and Released on the gamepad button fire once per press or release.

## Audio buses

Real engines never play every sound at one master volume. They route sounds through buses — named groups with their own faders — and HydraScript ships three: **Music**, **SFX**, and **UI**. Open the **Audio** tab to set each bus's volume (0-100%) or mute it. Those are the starting levels; blocks can change them while the game runs.

The buses are not just volume knobs. Each one handles sound the way its job needs:

- **Music** streams. A long track plays through an audio element and is never fully loaded into memory, so a 3-minute song costs almost nothing. Only one track plays at a time: playing a new one replaces the old, and **Stop Music** halts the stream. Music loops by default (there is a Loop switch on the block).
- **SFX** and **UI** are memory-resident. Each file is decoded once and kept in memory, so rapid repeats — jump, coin, hit, click — play instantly with no re-fetch. SFX allows 8 sounds at once, UI allows 4; past the limit the new sound is quietly dropped.

Every **Play Sound** block picks a bus (old blocks default to SFX, so nothing changes for existing projects), plus its own volume and **pitch**: 1 is normal, 2 is one octave up, 0.5 is one octave down. For a streamed track, pitch also nudges the tempo — that is how playback-rate pitch works. The final loudness is always master volume times bus volume times the block's volume, so muting a bus (or setting it to 0) silences everything on it without touching any blocks.

The **Master** fader at the top of the Audio tab scales every bus at once — the single volume control for a settings screen, starting at 100%. Existing projects have no master value saved, so they keep playing at full volume exactly as before.

Nine **Audio** blocks round out the pillar: **Set Bus Volume** (fade the music before a boss fight, duck the SFX in a menu), **Set Bus Muted** (the building block for a settings-screen mute toggle), **Set Master Volume** (runtime control for the master fader), **Stop Music**, **Pause Music** / **Resume Music** (pause keeps the track's position; a tone played on the Music bus cannot pause), **Stop All Sounds** (silences the music track plus every still-ringing SFX and UI voice — the cutscene silencer), the **Music Playing** condition (true while a track is streaming and not paused; invert it to detect "the song ended" and start the next one), and **Play Sound at Position** (below). Sounds keep playing while the game is paused — pausing freezes the world, not the soundtrack. Everything works the same in the preview and in exported games.

## Positional audio

A sound can play from a place in the world instead of from nowhere. **Play Sound at Position** takes the same sound as Play Sound — a built-in tone or an uploaded audio file, on any bus, with its own volume and pitch — plus a place: pick **At object** (the sound plays from that object's center), or leave the object blank and give an **X** and **Y** point instead. The listener is the center of the screen. Right on top of it the sound plays at full volume; as the source moves away it gets quieter in a straight line, reaching silent at the **Hear within (px)** distance (600 by default, 50 to 5000). Past that distance nothing plays at all — no voice is taken, so a hundred far-away coins cost nothing. The sound also pans: a source to the left of the screen center comes out of the left speaker, and the further left it sits (up to the hear-within distance) the harder it pans.

Two practical uses cover most games. A pickup or a doorbell that should only be heard nearby: put the block on the collision event with the object as the source, and the player hears it exactly when they are close enough to care. An ambient sound that should follow a place: a waterfall or a humming machine plays at its X/Y point on a loop-ish trigger (a repeating timer), so walking toward it makes it swell and walking away makes it fade.

A few honest limits. The fade is linear only — half the distance is half the volume, with no other curve to pick. The listener is always the screen center; it cannot follow an object, and there is no Doppler effect. Stereo pan only reaches sounds played through the WebAudio graph (built-in tones and decoded SFX/UI assets): a streamed track (a Music-bus asset, or any asset the runtime falls back to an audio element for) still gets the distance volume, but no left/right pan. A failed distance or position number warns in the diagnostics and plays nothing; a missing object stays quiet, and the block validator flags a misspelled object name in the editor before the game even runs. Scoped variables are run state too: global and object scopes survive scene switches inside a run and reset only on a fresh run, while the scene scope resets every time its scene loads — a fresh visit to a scene starts with no scene variables. They never travel in save slots — persist a value through Read Scoped Variable into a flat variable, and Set Scoped Variable from it after Load Game. Lists and dicts can be stored by copying a variable that already holds one, and a nested path write builds the containers it needs (a list of dictionaries grows one Set Nested Value at a time); object references live inside structures too (Store Object In Structure writes a handle at a path, Read Object From Structure reads it back), and For Each Field walks a structure one field at a time, handing the body the key and the value each round. The Scoped Variable Check compares numbers numerically and text/bool as text; a list or dict never matches ==. There is no script-API surface for scoped variables yet — use the blocks. A scene definition applies to every scene — there is no per-scene definition yet, so a coins counter that starts at 0 starts at 0 in every level.

## Pathfinding

An enemy that chases the player in a straight line gets stuck on the first wall it meets. **Follow Path** walks around the walls instead. It treats the scene's tilemap as the maze: every solid tile is a wall, every other cell is open floor. Give it an **Object** (the walker), a **Destination object** (or leave the object blank and give an **X** and **Y** point), and a **Speed** in pixels per second (100 by default, 1 to 2000). When the block runs, the engine finds the shortest route with A* — eight-direction movement that never cuts the corner between two wall tiles — smooths the zigzag into clean straight runs, and then walks the object along the waypoints one frame at a time until it arrives.

Two conditions read the walk. **Has Path** is true while the object is still on the move; **Path Finished** is true once it has arrived (and stays true until a new Follow Path or a Stop Path clears it). Both read every frame, even while paused. The usual shape is a chase loop: on a timer or on a collision, run Follow Path at the player; on Path Finished, do whatever happens next — start the attack, open the door, or roll a new destination for a patrol. **Stop Path** halts a walker where it stands, which is how a stun or a cutscene interrupts a chase.

A few honest limits. Walls come from tilemap solid tiles only — a wall built from sprites does not block a path, so build mazes on a tilemap. The path is computed once, when the block runs: if the destination moves, the walker keeps walking to where it was, so re-run Follow Path on a timer for a moving target. One path per object — a new Follow Path replaces the one already walking. A destination with no route (walled off, or sitting inside a wall) warns in the diagnostics and the object stays put; a failed speed or position number warns and holds the same way, and a missing object stays quiet. While a path is active the object's velocity reads zero, so physics never fights the walk — path following is position movement, like Move Toward, and works best on objects without gravity. Paths slow with the time scale and freeze while paused, like everything else in the world sim.

## AI behaviors

A chaser that runs in a straight line at the player gets stuck on the first wall it meets, and hand-building a chase out of timers and Follow Path blocks is fiddly. **Set AI Behavior** gives an object a brain instead: pick a **Behavior**, and the object decides where to walk on its own, re-planning through the pathfinder so it walks around the walls.

- **Patrol** walks between **Patrol point A** and **Patrol point B** in a loop — a guard on a route. The points are objects (hidden markers work well), looked up live, so a moving point drags the patrol with it; a missing point holds the patrol quietly where it stands.
- **Chase** walks at the **Target object** while it stays within **Range** (300 pixels by default), re-planning every half second so a moving target stays caught. Past the range the enemy stops and waits for the target to come back in range.
- **Flee** walks away from the target while it stays within range — a deer that bolts when the player gets close — picking the first walkable spot at range distance in the away direction, fanning out when straight away is a wall. Past the range it stops, safe for now.
- **Wander** picks a random walkable spot within range of where the behavior was set, walks there, idles for a beat, and picks again — a villager strolling around the square.
- **None (stop)** clears the behavior, the same as **Stop AI**.

**Speed** is in pixels per second (100 by default, 1 to 2000 — the same range as Follow Path). A bad speed or range number warns and holds, and a missing object stays quiet. A new Set AI Behavior replaces the one already running, and it clears the walking path so the brain always plans fresh.

Two conditions read the brain. **AI Behavior** is true while the object runs the picked behavior — use it to switch a guard from patrol to chase when the player is spotted, or to play the flee animation while a deer runs. **Target In Range** is true while the target object is within Range pixels of the object, center to center — use it to spot the player, to trigger a guard barking, or to end a flee once the target is far away. Both read every frame, even while paused. The usual shape is a guard that patrols until Target In Range fires, then Set AI Behavior to chase; when the player escapes past the range, the chase stops on its own and a second rule can put the guard back on patrol.

A few honest limits. Behaviors steer through the pathfinder, so walls come from tilemap solid tiles only. One behavior per object — a new Set AI Behavior replaces the one already running. Chase and flee re-plan every half second rather than every frame, so a fast target can juke a chaser for a moment. Behaviors are run state: a fresh scene load starts with no behavior, and none travels in save slots. Behaviors slow with the time scale and freeze while paused, like everything else in the world sim.

## Virtual joystick

A keyboard game is unplayable on a phone, and a phone game needs a stick on the glass. The **Joystick tab** (in the inspector) sets up the on-screen stick: a fixed base circle in a screen corner with a knob the player drags to steer. It is off by default — turn **On by default** on to have it from the start, or flip it during play with the **Enable Joystick** / **Disable Joystick** blocks (a level that needs touch controls can turn it on, a menu scene can turn it off).

The stick feeds the two systems the game already has, so no new wiring is needed to steer:

- **Variables.** Every frame the stick writes its tilt into two game variables — **Left / right variable** (joystickX by default) and **Up / down variable** (joystickY by default), each -1 to 1: left is -1, right is 1, up is -1, down is 1, and released it reads 0, so movement stops on its own. Chain a **Joystick Tilt** condition, or move the hero by joystickX each frame, and the character steers. Leave a variable blank to skip it.
- **Named actions.** The stick can drive up to four named input actions from the Inputs tab — **Tilt left drives**, **Tilt right drives**, **Tilt up drives**, **Tilt down drives**. Tilt past a third of the way and the action reads held, with just-pressed and released edges exactly like a key. Name Move Left, Move Right, and Jump, and the keyboard game becomes a phone game with no new blocks at all.

**Base position** picks the corner (bottom-left by default, bottom-right, or a **Custom position** with its own X/Y in screen pixels). **Base radius** (20 to 200, 60 by default) and **Knob radius** (8 to 100, 24 by default) size the circles. **Dead zone** (0 to 0.9, 0.15 by default) is the slack around the center where the stick reads exactly 0, so a resting thumb never drifts the player; past it the tilt rescales, so full tilt still reads 1.

Two conditions read the stick. **Joystick Active** is true while the player is steering — grabbed and tilted past the dead zone — so a held-but-centered stick reads quiet. **Joystick Tilt** is true while the stick tilts the picked way (**Any direction**, **Up**, **Down**, **Left**, or **Right**) past the **Min tilt** (0 to 1, 0.5 by default). Both read every frame, even while paused. The usual shape is a platformer that moves left and right on joystickX and jumps on Joystick Tilt up, or a twin-stick-free top-down game that drives Move Left / Move Right / Jump straight from the named actions.

A few honest limits. The base is fixed at its anchor — it does not float to where the finger lands, so the player always reaches for the same corner. One stick only: there is no second stick for a twin-stick shooter yet. A press only grabs the stick when it starts inside the base (plus a small slack ring); a press anywhere else is a normal click or touch, so buttons and touch zones keep working — but a grabbed pointer cannot also click a button underneath the stick. A mouse drag grabs the stick too, so the same game can be playtested on a desktop without a touchscreen. The stick is run state: a fresh run starts from the Joystick tab's default, and it never travels in save slots.

## Health and damage

Every action game needs something that can take a hit. Each object carries two numbers: **Max health** (how much it can take, 1 to 10000, 100 by default) and **Health** (how much is left). Set them in the Inspector **Health** section, and turn **Show health bar** on to draw a small bar above the object while the game runs — green while over half, amber while over a quarter, red below — so the player sees the hit land without a single extra block.

Four actions move the numbers:

- **Damage Object** takes hit points off, stopping at 0 — an enemy at 10 hit points hit for 25 reads 0, not -15. Use it when a bullet lands, a spike touches the player, or a trap fires.
- **Heal Object** gives hit points back, stopping at the max — a potion never overfills the bar. Use it when the player grabs a heart, stands in a healing zone, or levels up.
- **Set Health** writes an exact value, clamped between 0 and the max — reset the player to full at a checkpoint, set a boss to half health when the fight starts, or load a saved health value back after Load Game.
- **Set Max Health** moves the ceiling — a level-up raises it, a curse lowers it. The current health re-clamps to the new ceiling, so a lowered max never leaves health above the bar.

Two conditions read the numbers. **Health** is true while the object's health compares with the value the picked way (at least 50, exactly 0, below a quarter) — use it to flash a low-health warning, to make a boss change attacks under half health, or to heal the player only when hurt. **Object Died** is true while the object's health is 0, and it fires once on the killing hit — chain Destroy Object, Hide Object, or a death animation after it. The block never destroys the object itself: the game decides what death means. Both read every frame, even while paused.

**Damage feedback.** A hit should feel like a hit. Three blocks make it land. **Show Damage Number** pops a floating number above the object — it rises and fades out over about a second — so place it right after Damage Object with the same amount and the player sees the 20 they just dealt. The number is display only; it never changes health. **Make Invincible** gives the object a shield for the picked seconds, and Damage Object skips it while the shield holds — the classic loop is Damage Object followed by Make Invincible for 1 second, so a second hit the next frame does nothing instead of shredding the player. 0 seconds clears the shield at once, and Heal and Set Health still apply to a shielded object: the shield blocks hits, not help. **Knockback Object** pushes the object away from a source object, or from an X/Y point when From object is blank — pair it with Damage Object so the enemy staggers back from the explosion. When the source sits exactly on the object, the push goes straight up. **Is Invincible** reads the shield back: true while it holds, so flash the sprite or show a shield icon only while it lasts. It reads every frame, even while paused, like the other health conditions.

**Checkpoints and respawn.** When the player dies, they should come back at the last checkpoint, not at the start of the level. Put a flag (or any object) at each safe spot, and run **Set Checkpoint** on it when the player touches it — the checkpoint is the object's top-left corner, or the X/Y point when no object is named. A new checkpoint replaces the old one, so the respawn moves forward as the player passes each flag. Then chain **Respawn Object** after **Object Died**: it sends the object back to the last checkpoint, zeroes its velocity, stops a walking path, and refills the health to full while **Restore health** is ticked (untick it for a hardcore run where the player comes back hurt). With no checkpoint set yet, the respawn sends the object back to where it started the scene — so the loop works even before the player reaches the first flag. **Clear Checkpoint** forgets the point, so the next respawn goes home instead; use it when a level restarts or after a game over. Two conditions read the state: **Checkpoint Set** is true while a checkpoint is recorded (invert it to flash "no checkpoint yet" at the start), and **Respawn Count** is true while the scene's respawn count compares with the value the picked way — at least 3 for a three-lives game over. Both read every frame, even while paused.

**Enemy spawner.** When the player comes back, the enemies should keep coming too. **Start Spawner** names a spawner — the Spawn object to clone (an enemy, a coin, a power-up), the spot to clone it at (the top-left corner of the At object, or the X/Y point when no object is named), how often (Every seconds), how many may be alive at once (Max alive), and how many in total (Total). Max alive 0 means no cap, Total 0 means endless. The first spawn lands after one interval, never at once, so a wave has a readable beat — start the spawner at gameStart with an interval of 2 and a goblin appears at the spawn pad every 2 seconds. The cap counts every live object with the template's name, however it got there, so killing an enemy frees the slot on the next tick. Set a Total for a wave that ends: once it has spawned that many, the spawner stops on its own. **Stop Spawner** stops one by name, or all of them when the name is blank — use it when the wave is beaten or the player leaves the area. Two conditions read the state: **Spawner Active** is true while the spawner runs (a spawner that reached its total reads as stopped, so invert it to open the goal door once the wave is done), and **Spawned Count** is true while the spawned total compares with the value the picked way — at least 10 for a ten-spawn wave gate. **Read Spawned Count** copies the total into a variable, so you can show it, save it, or compare it. All three reads work every frame, even while paused. A spawner never sets an AI behavior or a path on what it spawns — chain Set AI Behavior after the spawn if the newborn should chase.

**Lives and game over.** The comebacks run out. The player starts with 3 lives — the classic arcade default — and every death should cost one. The loop is three blocks: **Object Died** → **Lose Life** → **Respawn Object**, so the player loses a life and comes back at the checkpoint in one chain. **Game Over** fires once, exactly when the last life is lost — chain it to Switch Scene for the game-over screen, or to Show for a game-over banner. **Set Lives** writes the count outright (set it once at gameStart; 0 starts the game already over), **Add Lives** tops it up for a 1-up or a level bonus, and **Read Lives** copies the count into a variable so a label can show it or Save Game can keep it. The **Lives** condition is true while the count compares with the value the picked way — at least 1 while the player still has a life left, exactly 0 when the game is over — so gate a "last life" warning on it. Lives survive scene switches inside a run, so the lives left in level 1 are the lives left in level 2, and they reset only when the game starts over. Gaining a life after game over clears it, so losing the last life again fires Game Over again — that is how a continue works.

**Experience and leveling.** Killing things should make the hero stronger. **Add XP** gives experience points — 10 is one coin or one defeated enemy, so chain it after Object Died on the enemy and every kill pays out. The level is derived from the total: level = floor(XP / XP-per-level) + 1, with 100 XP per level by default, so ten 10-XP kills is level 2. **Set XP Per Level** rewrites what one level costs — 50 levels up twice as fast, 200 makes every level a grind — and changing it re-levels at once, since the level is always just the math on the current numbers. **Level Up** fires once, exactly when the level rises — chain it to Heal Object for a level-up heal, Play Sound for the fanfare, or Show for a LEVEL UP banner. **Read XP** and **Read Level** copy the total and the level into variables, so a label can show them or Save Game can keep them (then Set XP from the saved value after Load Game). The **XP** and **Level** conditions compare the total and the level with the value the picked way — gate a locked door on Level at least 2, or a stronger enemy wave on XP at least 500. All three conditions read every frame, even while paused. XP survives scene switches inside a run, like lives, so the XP earned in level 1 is the XP earned in level 2, and it resets only when the game starts over.

**Level-up rewards and stat growth.** A level up should make the hero stronger, not just change a label. Chain **Level Up** to the Growth blocks and every level pays out. **Grow Max Health** raises the object's max health by the amount (10 by default) and heals it by the same amount, so a level up both toughens the hero and tops the bar back up; turn Heal off to raise the ceiling without the heal. **Grow Damage** adds a lasting damage bonus (2 by default), and **Melee Attack** and **Shoot Projectile** add the attacker's bonus to their block damage, so a hero that leveled twice with +2 each hits for +4. **Grow Speed** adds a lasting speed bonus (50 by default) that the **Dash** block adds to its speed, so dashes get longer and quicker as the levels pile up. **Level Reward** grants a whole reward in one block: Balanced (+10 max health, heal 10, +2 damage), Tank (+20 max health, heal 20), Striker (+5 damage), or Swift (+50 dash speed). Every bundle is just the Grow blocks packed together, so you can always rebuild the same reward by hand. **Read Max Health Bonus**, **Read Damage Bonus**, and **Read Speed Bonus** copy one object's bonuses into variables, so a label can show them or Save Game can keep them. Growth follows the object's name across scenes, like XP, so the hero keeps its bonuses from level 1 into level 2, and it resets only when the game starts over.

**Enemy scaling.** The hero grows stronger every level, so the enemies should too, or the game gets easier the longer a run goes on. **Set Enemy Level** writes an enemy's level — 1 is an unscaled enemy, and at the default rates (10 health and 2 damage per level) a level-3 enemy is +20 max health and +4 damage. The max health rises by the bonus and heals by the same amount when it rises, and the damage bonus rides along on the enemy's **Melee Attack** and **Shoot Projectile** hits, so a scaled goblin actually hits harder. **Set Scaling Rates** rewrites what one level is worth for that enemy — give a boss 50 health per level and a minion 5, and they scale apart. **Scale to Hero Level** copies the hero's current level onto the enemy in one block: chain it after **Level Up** to re-scale every enemy still alive, or put it on a gameStart row so each scene's enemies arrive at the hero's level. **Read Enemy Level**, **Read Scaled HP Bonus**, and **Read Scaled Damage Bonus** copy the level and bonuses into variables, so a label can show them or Save Game can keep them. The **Enemy Level** condition is true while the enemy's level compares with the value the picked way — gate a stronger wave on Enemy Level at least 3. Scaling follows the object's name across scenes, like growth, so the goblin keeps its level from level 1 into level 2, and it resets only when the game starts over.

**Boss encounters.** A run needs a climax: one big fight at the end of it. **Start Boss** names the boss object and picks how many phases the fight has — 2 to 5, 3 by default — and a wide health bar with the boss's name appears across the top of the screen. The phases are equal slices of the boss's health bar, so with 3 phases the fight is in phase 1 down to two thirds of its health, phase 2 down to one third, and phase 3 to the end. **Boss Phase** is the condition that reads the phase number, so the behavior per phase is ordinary blocks: Boss Phase at least 2 → **Set AI Behavior** to chase faster, **Set Scaling Rates** harder, **Start Spawner** for minions. **Boss Active** is true from Start Boss until **End Boss**, even before the boss spawns — gate the fight music and the arena doors on it. **Read Boss Phase** copies the phase number into a variable, so a label can show it or Save Game can keep it. **Show Boss Bar** and **Hide Boss Bar** toggle the bar without ending the fight, so a cutscene can clear the screen and bring it back. Nothing ends the fight on its own: the killing blow fires **Object Died** like any other death, so chain **End Boss** after it, on the same row as the win screen or the XP reward. One boss at a time — starting a second boss replaces the first — and the fight survives scene switches inside a run, resetting only when the game starts over. A boss that has not spawned yet reads phase 0 and shows no bar until a live object with its name exists.

**Object tags.** A tag is a plain label on an object — goblin, coin, boss, collectible — so a whole group of objects can be asked about at once instead of one name at a time. The Inspector **Tags** section lists an object's tags as chips, with an add box: those are the permanent tags, the ones a fresh run starts with, and a scene that loads again restores them. **Add Tag** sticks a label on a live object while the game runs, **Remove Tag** takes one off, and **Clear Tags** takes them all off — runtime tags last until the scene loads again. **Has Tag** is true while any live object with the name carries the tag, so a goblin can be elite and a coin can be golden. **Tagged Count** compares how many live objects carry the tag, so the classic win row is Tagged Count goblin equals 0 — every goblin gone. **Read Tagged Count** copies that count into a variable, so a label can show "goblins left: 3" or Save Game can keep it. **Pick Nearest Tagged** and **Pick Farthest Tagged** pick one tagged object by distance, **Pick Random Tagged** picks one at random, and **Pick Tagged Object Into Variable** holds one in a variable so the game can keep track of it even when the tagged objects have different names. **For Each Tagged Object** walks the whole group one at a time — damage every goblin, move every coin — and when its Object variable is named it holds the current object each time round, so Read Object Property can read it. Matching ignores capitals, so Goblin and goblin are the same tag, and an object holds at most 16. One honest limit: a tag never travels in save slots, so persist a count through Read Tagged Count the way quests and inventory do.

**Minimap.** A big level needs a small map: the **Minimap** section in Scene Settings turns one on for the scene — a corner (top right by default), a size in pixels (80 to 400, 160 by default), and a zoom (1 fits the whole scene). Every live object draws as a dot at its position: the boss red and large while a fight runs, an object tagged `player` white and large, any other tagged object in its tag's color, untagged objects gray. A white rectangle outlines what the camera sees, so the player can tell where they are in the level at a glance. **Show Minimap** and **Hide Minimap** turn it on and off while the game runs — hand the player the map when they pick it up, clear the screen for a cutscene — and **Set Minimap Size** and **Set Minimap Zoom** change how it draws for the current scene only. Zoom above 1 shows a window around the camera instead of the whole level: 2 shows half the level, 4 shows a quarter, so a zoomed map follows the player. **Minimap Visible** is true while the map shows, so a toggle button or a hint label can gate on it. Each scene decides for itself whether it has a map — a scene with the map off stays off even after the last scene showed one — and the map never travels in save slots.

**Attach.** One object can ride on another: **Attach Object To Object** links a child to a parent, so the child follows the parent everywhere at a fixed offset — a sword in the hero's hand, a hat on a goblin, a name tag above an NPC. Leave the offsets blank to keep the spacing the objects already have, or give numbers in world pixels from the parent's top-left corner to the child's. The attach is applied after every other movement each frame, so a dash or a path step moves the parent and the child still lands exactly on it. **Detach Object** drops the link, **Set Attachment Offset** slides an attached child to a new spacing without re-attaching it, and **Is Attached** is true while the object rides on something (name a parent to ask about that parent only). A child keeps one parent — attaching it again replaces the old link — and a link that would close a cycle is refused. Links clear when the scene loads again, so re-attach in a gameStart row, and a link to an object that has not spawned yet starts working the frame it appears.

**Scoped variables.** One flat pile of variables is not enough once a game has more than one level: a "coins" counter in level 1 and a "coins" counter in level 2 would be the same variable, and two goblins could not each keep their own health. **Set Scoped Variable** stores a value in exactly one scope — **Global** keeps it for the whole run in every scene, **Scene** keeps it for this scene only and resets when the scene loads, **Object** keeps one value per object name, so the goblin's hp and the hero's hp are different variables under the same name. The value carries its type with it: a number stays a number, text stays text, true/false stays a bool, and a list or dict stays one (copied, never shared). **Read Scoped Variable** copies one back into an ordinary variable, so expressions, labels, and the old variable blocks can use it — a missing variable reads as 0. **Delete Scoped Variable** removes one, and **Clear Scoped Variables** empties a whole scope at once (leave Object blank to clear every object's). The **Scoped Variable Exists** and **Scoped Variable Check** conditions read every frame, even while paused: gate a door on the scene coins reaching 10, or run a row only the first time with an inverted Exists check that sets the variable at the end of the row. The object scope needs a name, not a live object — set a variable for an enemy before it ever spawns.

**Object references.** A variable can hold an object, not just a number or text: the value is a reference to one live object, kept by name and id. **Pick Object Into Variable** picks one — Nearest, Farthest, Random, or First among the live objects with a name, measured from the Near object when one is named and from the X/Y point otherwise — and stores it in a scoped variable, so the game can keep track of one goblin, one coin, one bullet and use it later. The pick also points the rest of the chain at the picked object, so a Damage Object chained after it hits that one goblin and not the others. **Read Object Property** reads one property of the held object back into an ordinary variable: X and Y position, width, height, rotation, velocity, health, max health, or its name as text. Is alive reads 1 while the held object is still live and 0 when it is gone, so pick, read alive into a flag, and branch on the flag is the way to ask whether a target still exists. Two physics queries return the same kind of data. **Raycast Into Variables** casts a ray from one point to another and stores the closest live collision object it hits, plus the distance to the hit; a miss writes -1 for the distance and clears the object variable, so the variable never holds a stale hit, and chained actions hit only the hit object. **List Overlapping Objects** lists every live collision object inside a circle and stores them as a list of references in a flat list variable, with the count in a second variable, so **For Each Item** can walk through them one at a time: each round the body reads the current object's properties with Read Object Property and its actions hit that one object. **Spawn Object Into Variable** spawns a copy of an object and stores the clone as a reference, so the game can keep track of one spawned enemy, one bullet, one coin and act on only that one: the spawn also points the rest of the chain at the clone, so a Damage Object chained after it hits that one clone and not the others. **Destroy Object In Variable** destroys exactly the object a variable holds, not every object with that name, so a spawned enemy can be removed without touching the original. A spawn of a missing source clears the variable, so it never holds a stale clone. A few honest limits: a reference never stores the object itself, only its name and id, so a reference to a spawned clone goes stale when the clone is destroyed or the scene switches, and a stale reference reads as 0 (empty text for Name) instead of retargeting a different object with the same name. No live object to pick stays quiet and writes nothing. The Live variables panel shows a held object by its name, like object (goblin), or object (none) when the reference is empty.

**The Variables manager.** The Variables tab in the Scene inspector lists every variable the game starts with, grouped by scope, with its starting value. Add one there — name, scope, object when it is an object variable, type, starting value — and the game begins with it: no block has to set it first. Global definitions seed when the game starts, object definitions seed with them, and scene definitions seed every time their scene loads, so each visit starts from the starting value. Click a name to rename it, change a value to rewrite where the game starts from, and the × deletes it. While a preview is running, the Preview tab's Live variables panel shows what the game holds right now — every definition plus any variable a block created mid-run — updated as you play. The manager panel itself edits starting values only: change one there and the next run starts from it. The **Scoped Variables Demo** template (New Project) is the acceptance game for all of it: a global score, per-level coins, and one goblin HP shared across two levels — open it, play it, and watch the Live variables panel while you play.

**Loops.** When the same chain of blocks has to run more than once — spawn five coins, count a variable up to ten, keep trying until something is true — use a loop instead of copying the chain. A loop block sits at the head of a row and the actions to its right on the same row are its body: **Repeat** runs the body a set number of times, **While** runs it until its test stops holding. Put the trigger condition above the loop block (on the row above, not in the same row), the loop block at the head of its row, and the body to its right; a condition, an empty cell, or the row end stops the body, and actions below the loop block are not the body. **Repeat** takes how many times and an optional counter variable: the counter reads 1 on the first time round, 2 on the second, up to the count, and the body reads it like any other variable — so Repeat 5 with a counter named i and a body that adds i to a sum gives 1 + 2 + 3 + 4 + 5. **While** takes two values and a comparison, and runs the body while the test holds: change a variable inside the body and test that variable, so the loop has a way to finish — a test that never changes stops after 1000 times with a warning. **Break** stops the innermost loop at once and the game carries on after it; **Continue** skips the rest of this time round and starts the next one. Outside a loop, Break and Continue warn and do nothing. **For Each Item** walks through a list instead of counting: it runs the body once per item, the item variable holds the item each time round, and the index variable, when named, counts 1, 2, 3. Build the list first with the array blocks (Push To Array and friends), then add the items up. A list with more than 1000 items runs only the first 1000 and warns, and a variable that holds no list warns and nothing runs. **For Each Object** walks through the live objects with one name instead: it runs the body once per object, and body actions that target the object hit one object at a time, the current one, so the same chain can heal every goblin or move every coin. The index variable counts the objects the same way. No live objects runs nothing. **For Each Field** walks through a structure instead: it runs the body once per field, the key variable holds the field name each time round and the value variable holds the field's value, and the index variable counts the same way. When a field holds an object handle, the body round also points the rest of the chain at that live object, so a squad stored as a structure can be walked one member at a time. A structure with more than 1000 fields runs only the first 1000 and warns, and a variable that holds no structure warns and nothing runs. Two honest limits: the body cannot read the current object's position into a variable yet, and a dict is not a list, so For Each Item over a dict warns and holds — walk a dict with For Each Field instead. Loops nest — an inner loop in a body runs all the way through once per outer round — and a body can call a function. Three caps keep a bad loop from freezing the game: Repeat clamps to 1000 times, While stops after 1000 times, loops nest at most 8 deep, and a per-frame budget of 10,000 body actions bounds nested loops as well. Two things to know before you use them: a loop body runs all at once inside one frame, so a While that waits on a key press or a timer will never see it change mid-loop — test a variable the body itself changes instead. And do not put a condition right after a loop body on the same row: a condition fires the actions around it, so it would fire the body's last action once more on its own.

**Custom events.** When one chain needs to tell another chain something happened — a coin scores, a boss dies, a door opens — use an event instead of polling a variable. **Broadcast Event** sends a named event, and **On Event** with the same name hears it: the blocks to the right of the listener run once per broadcast. Put the broadcast in the chain that knows (after Set Variable, so the listener can read the value the broadcast set), and the listener wherever the reaction belongs — a different row, a different scene's grid, the global grid. The name is plain text, so spell it exactly the same on both blocks; a listener for a name that is never broadcast stays quiet, with no warning. A listener after the broadcaster in the grid fires in the same frame; a listener before it fires on the next frame — either way exactly once per broadcast, and several broadcasts of one name in one frame still fire it once. A broadcast every frame fires the listener every frame. An event carries no value with it: set a variable first when the listener needs a number or a name. The event state survives scene switches inside a run, so a broadcast in one scene reaches a listener in the next scene on the next frame.

**Functions.** When the same chain of blocks shows up in three places — add two numbers, roll damage, check a password — write it once as a function and call it from anywhere. The **Functions** tab in the Scene inspector lists the game's functions: add one with a name and up to eight parameters (comma-separated), then click **Edit body** to open its own grid, a scope tab marked with ƒ, and build the chain there like any other grid. **Call Function** runs it once and stores the return value in an ordinary variable (leave it blank to throw the value away): pick the function, and the panel shows one argument field per parameter, labeled with the parameter name — fill them in as expressions, and the parameters arrive inside the body as **local** variables — a fourth scope only that call can see — so the same body adds 3 + 4 one moment and 10 + 20 the next. **Return From Function** hands a value back and stops the rest of the body; a function with no Return returns 0. A body never runs on its own, only when Call Function names it, and a gameStart block inside a body fires only on the first call of the run — so a body can count its own calls or set itself up once. Calls nest, and a function can call itself, but the stack caps at 32 deep: the 33rd call is skipped with a warning and returns 0. Rename a function and every Call Function block naming it follows; deleting one asks first when calls still name it. Duplicate copies a function under a new name like add copy, with the same parameters and a copy of the body, so a variant starts from a working chain instead of an empty grid. Each row also says how many times the function is called, or that it is not called yet. If you type a duplicate parameter, or more than eight, the panel keeps the first eight unique names and tells you which ones it dropped instead of trimming the list silently. A few honest limits: arguments are expressions, so parameters always arrive as numbers — set text locals inside the body with Set Scoped Variable if the body needs text. Eight parameters at most, and the Call Function panel shows one argument field per parameter, labeled with the parameter name. The diagnostics panel also checks function bodies like any other grid: it flags a Call Function that names a function that does not exist, a Return From Function placed outside a function body, and a bad expression inside a body. A body can read and write the global, scene, and object scopes like any grid, but its locals die with the call — read one after the call and it is gone.
A few honest limits. Health lives on the live object: a fresh run starts at the Inspector values, damage during a run never rewrites the project, and health never travels in save slots — persist it through a variable (read it with the Health condition into Set Variable on save, Set Health on load) the way quests and inventory do. Damage numbers are plain text popups with no critical-hit styling, and they never travel in save slots either — a fresh scene starts with none showing. Invincibility blocks Damage Object only: Heal and Set Health still apply, and it does not stop physics, timers, or other blocks from touching the object. Knockback moves any non-static, non-text object, and the object's max speed caps how fast it can fly, so a heavy object with a low max speed barely moves. There is no script-API surface for damage feedback yet — use the blocks. Checkpoints are run state too: a fresh scene starts with none set and a zero respawn count, and neither travels in save slots — persist the count through a variable the way quests and inventory do. One checkpoint per scene, and it is the object's top-left corner, not its center. An AI behavior keeps running after a respawn (the brain re-plans from the new spot — stop it yourself with Stop AI if the respawn should calm the enemy down), and the shield from Make Invincible is left alone — chain Make Invincible after Respawn Object for a spawn shield. There is no script-API surface for checkpoints yet — use the blocks. Spawners are run state too: a fresh scene starts with none running, and the spawned count never travels in save slots — persist it through Read Spawned Count into a variable, and re-start the spawner after Load Game. A spawner never survives a scene switch, so a wave from level 1 never keeps spawning into level 2. One spawn per interval tick per spawner, and the clone's top-left corner lands at the spawn point, not its center. A named spawn-point object that is missing or destroyed holds the spawn until it exists again. There is no script-API surface for spawners yet — use the blocks. Lives are run state too: they survive scene switches inside a run and reset only on a fresh run, and they never travel in save slots — persist them through Read Lives into a variable, and Set Lives from it after Load Game. One count for the whole game, and losing a life never respawns anything on its own — chain Respawn Object after Lose Life for the comeback. There is no script-API surface for lives yet — use the blocks. XP is run state too: it survives scene switches inside a run and resets only on a fresh run, and it never travels in save slots — persist it through Read XP and Read Level into variables, and Set XP from them after Load Game. One XP total for the whole game, with one flat XP-per-level number — no XP curves, so level 10 costs the same 100 XP as level 2. Level Up is consumed on read, so place one Level Up row per reward chain — a second Level Up row in the same grid would see nothing, because the first read already announced the level. Lowering XP below the announced level never re-fires until the level climbs past it again. Gaining XP never heals, damages, or unlocks anything on its own — chain the Level Up condition after Add XP for the reward. There is no script-API surface for XP yet — use the blocks. Growth is run state too: it survives scene switches inside a run and resets only on a fresh run, and it never travels in save slots — persist it through the Read Bonus blocks into variables. The ledger survives a scene switch, but the live max health is per-scene authored state: a fresh scene's hero starts at its own authored max health, and the next Grow Max Health builds from there, while the damage and speed bonuses apply in full in every scene because they are read from the ledger at use time. Growth is per object, not per level curve — the author picks the amount per reward row, so a flat +2 damage every level is the default shape, with no automatic stat scaling unless the author wires it. The speed bonus quickens dashes only: the Dash block is the one movement block with a speed, and walking speed comes from Set Velocity and Move Toward blocks with their own speeds. Damage Object never adds a bonus: it names the victim, not an attacker, so read the bonus and add it in the amount expression instead (10 + dmgBonus). There is no script-API surface for growth yet — use the blocks. Scaling is run state too: it survives scene switches inside a run and resets only on a fresh run, and it never travels in save slots — persist it through the Read blocks into variables. The level survives a scene switch, but the live max health is per-scene authored state: a fresh scene's enemy starts at its own authored max health, and the next Set Enemy Level, Set Scaling Rates, or Scale to Hero Level builds from there, while the damage bonus applies in full in every scene because it is read from the ledger at use time. Nothing scales on its own unless the author wires it — chain Level Up to Scale to Hero Level, or put Scale to Hero Level on a gameStart row. Scaling is per enemy, not per level curve — the author picks the rates per enemy, so a flat +10 health and +2 damage per level is the default shape. Damage Object never adds a scaling bonus either, for the same victim-not-attacker reason. Scaling never touches speed. There is no script-API surface for scaling yet — use the blocks.

## Movement abilities

Until now jumping meant an Apply Force preset or Set Velocity plus an On Floor gate you wired by hand. The **Movement** blocks give the player the four classic platformer moves, and the Inspector **Movement** section sets them per object: **Max jumps** (1 is a single jump, 2 is the classic double jump), **Coyote time** (seconds of grace after walking off a ledge), **Jump buffer** (how long a jump press is remembered for), **Wall slide max fall** (px/s the hero may fall while sliding down a wall, 0 turns the slide off), **Wall jump speed**, and **Wall jump push**. An object you never touch keeps one jump with no coyote, no buffer, no slide, and no wall jump, which is exactly the old behavior.

**Jump** is the one block that does the right thing. Chain it after a key press or an action input (Key Pressed Space, or Action Input Jump Just pressed) and it jumps: on the ground it jumps, just after walking off a ledge it still jumps while the coyote window holds, and in the air it jumps again up to Max jumps. A press that arrives with no jump left is remembered for the buffer window and fires the moment the object lands, so a jump pressed just before landing still counts instead of being lost. Jump speed 12 is a solid platformer jump — raise it for a floatier hero, lower it for a heavy one. Landing refills the jumps, so the count is always full on the ground.

**Dash** bursts the object in one direction — Left, Right, Up, or Down — at an exact speed in pixels per second, for a fixed duration, then a cooldown before the next one. 400 px/s for 0.15 seconds covers about 60 pixels: a snappy burst across a gap. Gravity cannot droop the burst and friction cannot decay it, so the dash always travels the same distance. A dash that is already running or still cooling down is ignored, so one press is one dash — the classic loop is Key Pressed Shift → Dash, with Cooldown 0.5 keeping it from becoming a flight button.

Three blocks rewrite the jump config while the game runs: **Set Max Jumps** (a power-up that grants a double jump is one block — set it back to 1 when the power-up ends), **Set Coyote Time** (0.1 is the forgiving platformer feel, 0 turns it off), and **Set Jump Buffer** (0.1 means a press just before landing fires on landing, 0 turns it off). Two conditions read the state back. **Jumps Left** is true while the object's jumps left compare with the value the picked way — at least 1 while the player can still jump, exactly 0 while every jump is spent until the next landing — so show a double-jump icon only when the air jump is ready. **Is Dashing** is true while the object is mid-dash, so spawn dash particles, play a whoosh, or chain Make Invincible after Dash to make the player untouchable while dashing. Both read every frame, even while paused.

**Wall slide** turns vertical walls into climbable shafts. Set a **Wall slide max fall** (60 px/s is a slow slide) and a hero pressing toward a solid wall while airborne and falling slides down it slowly instead of dropping — the slide only holds while the press holds, so releasing the key drops the hero at full speed. **Wall jump** is the way back up: **Set Wall Jump** picks the jump speed (12 matches the Jump block) and the push away from the wall (8 is a clear outward arc), and then the Jump block itself performs the wall jump while the hero touches a wall — up at the wall-jump speed, away at the push. It costs one air jump, so Max jumps still bounds the climb, and one wall jump per wall until the hero lands or reaches another wall: jump off the left wall, drift to the right wall, jump off that one, and so on up the shaft. **Wall Sliding** is true while the slide holds, so play a slide sound, spawn wall dust, or show a climbing hint while it reads true. It reads every frame, even while paused.

Grounded means standing on a solid object floor or a solid tilemap tile, so the moves work on tile levels too — a player standing on painted ground jumps and refills the same way as one standing on a platform object. A few honest limits. One dash direction per Dash block — no diagonal, no facing-relative dash; run two Dash blocks (one Left, one Right) behind a direction check if the dash should follow the player's facing. The dash moves the object directly, so it can sit inside a thin wall for a frame before the next physics step pushes it back out — keep dash targets away from paper-thin walls. Jumps never refill on an object that cannot be grounded (collision off), so use Set Velocity for flying objects. Walls are solid objects only — tilemap walls do not slide or wall-jump yet, and a one-way platform never blocks from the side. The slide reads the arrow keys or A/D directly, not remapped action bindings. The wall-jump push is a velocity set once, so if the game sets horizontal velocity from held keys every frame, the push lasts until the next frame's movement row — steer away from the wall after jumping. Pressing jump against the same wall again spends a normal air jump if one is left, instead of pushing off twice. Movement state is transient run state: a fresh scene starts with no dash in flight, no buffered jump, and a full jump count, and nothing travels in save slots — persist Max jumps through a variable the way quests and inventory do, and re-apply it after Load Game. There is no script-API surface for movement yet — use the blocks.

## Combat

Until now hurting an enemy meant hand-wiring a collision row plus Damage Object, and a fireball meant hand-wiring Spawn Object plus Move Toward plus another collision row. The **Combat** blocks give the player the two classic attack verbs, and both run through the same damage path Damage Object uses — so an invincible target skips the hit quietly, and Object Died still fires on the killing blow.

**Melee Attack** swings in front of the attacker. Pick the attacker, a **Damage** (10 is a solid sword hit), a **Range** in pixels (60 is a sword swing), a **Direction** — Left, Right, Up, or Down — and a **Cooldown** in seconds (0.5 keeps one press from becoming a blender). Every solid object whose center sits inside the 90-degree arc in front of the attacker, out to the range, takes the damage, and a white slash arc flashes for a moment so the swing reads even when nothing is in range. The classic loop is Key Pressed X → Melee Attack, with the cooldown keeping the swings honest. An attack pressed during the cooldown does nothing, the same way a dash on cooldown is ignored.

**Shoot Projectile** fires a copy of the projectile object from the shooter's edge. Pick the shooter, the **Projectile** object (make it a small sprite with collision on — a fireball, an arrow, a bullet), a **Direction**, a **Speed** in pixels per second (300 is a brisk fireball), a **Damage**, a **Lifetime** in seconds (2 is a shot that crosses a room and dies), and a **Cooldown**. The shot flies straight until it touches the first solid object — damaging it — or its lifetime ends, when the copy is destroyed. One hit per projectile, no piercing. The shooter never hits itself, and one projectile never hits another. The classic loop is Key Pressed Z → Shoot Projectile, with Cooldown 0.5 pacing the shots.

**Attack Ready** is true while the object's picked attack has cooled down — Melee or Shot — so gate a fire button on it instead of spamming a refused attack every frame. An object that never attacked reads as ready. It reads every frame, even while paused.

A few honest limits. One direction per attack — no diagonal, no facing-relative attacks; run two blocks (one Left, one Right) behind a direction check if the attack should follow the player's facing. Melee hits anything solid in the arc, walls included, so keep walls out of the swing or check the target name after the hit. A projectile stops at the first solid thing it touches, wall included, and never pierces. Projectiles move by direct position steps, like a dash, so one can sit inside a thin wall for a frame before the hit check lands. Combat state is transient run state: a fresh scene starts with no cooldowns spent, no projectiles flying, and no slash showing, and nothing travels in save slots. There is no script-API surface for combat yet — use the blocks.

**Rebuilding the attacks from primitives.** Melee Attack and Shoot Projectile are presets now — the friendly face over ordinary blocks, not the model for new work. Both come apart into block chains you can build by hand, and the chains below are the whole mechanism: nothing hidden, nothing you cannot change. The one-block versions stay, and they keep working exactly as before; the chains are the manual path, for when the preset's shape is not the shape you want.

**The melee rebuild, swinging right.** One row, triggered by Key Pressed X (or gameStart for a test swing). **List Overlapping Objects** draws a circle on the hero — center X `hero.posX + hero.width / 2`, center Y the same way, radius 60, layer mask set to the enemies' layer only so walls never enter the list — and stores the goblins inside it in `nearby`. **For Each Item** walks `nearby` one goblin at a time, item `foe`. The body reads the goblin back: **Read Object Property** X into `foeX`, Y into `foeY`. Then **Set Variable** `swingAng` to `Math.abs(Math.atan2(foeY + 20 - (hero.posY + hero.height / 2), foeX + 20 - (hero.posX + hero.width / 2)))` — the angle from the hero's center to the goblin's center, folded to 0..pi, with 20 the half-width of a 40-pixel goblin (use half your own goblin's width). Then **Damage Object** on `goblin` with the amount `swingAng <= 0.785 ? 10 : 0` — 10 inside the arc, 0 outside it. 0.785 is 45 degrees in radians, half the 90-degree arc; a goblin straight ahead reads 0, one behind reads pi, and the ones at the arc's edges read just under and just over the line. The test lives in the damage amount because a condition cannot sit inside a loop body: the body's rightward scan stops at a condition, so the per-item test has to be an expression. For the cooldown, lead the row with **Timer Elapsed** (`swingTimer` at least 0.5) and **Reset Timer** `swingTimer` at the end of the row. For the slash flash, spawn a slash sprite at the hero's edge in the same row and destroy it after 0.15 seconds with a second timer row, or fire a particle burst instead.

**The shot rebuild, firing right.** Five rows. Row 1 runs on gameStart: **Destroy Object** on the fireball template, then **Spawn Object Into Variable** — the fireball at the hero's right edge, into `shot` — then **Reset Timer** `shotTimer`. The template is only a mould: destroy it first, because while it sits live in the scene Pick Nearest can hand the flight row the template instead of the shot, and after the shot dies the template is the only fireball left, so the row would start flying the template itself. Destroying the live template does not touch the scene's definition of it, so later spawns still work — the key-press row below spawns from the same mould as many times as you like. Row 2 runs on always: **Read Object Property** on `shot`, alive into `shotAlive`, so every frame knows whether a shot is flying. Row 3 is the flight, gated on `shotAlive` being 1: **Pick Nearest** fireball near the hero re-acquires the clone every frame — the spawn hands the clone back once, but this row runs every frame and has to find it again — then **Move Toward Position** walks it toward a far point (X 10000, Y the hero's center line) at speed 5. The speed counts pixels per frame, so 5 a frame is 300 pixels a second at 60fps; 300 in that field would jump 300 pixels a frame and leap clean over the goblin. Row 4 is the hit test, on always: read the shot's X into `shotX` and Y into `shotY`, **List Overlapping Objects** centered on the shot (`shotX + 10`, `shotY + 10`, radius 24, enemies' layer) into `nearby`, then **For Each Item** over it. The body re-reads the shot's alive into `shotAlive` first — then **Damage Object** on `goblin` with the amount `shotAlive == 1 ? 10 : 0`, then **Destroy Object In Variable** on `shot`. That re-read is the canned one-hit rule: the first goblin in the list is damaged and the shot destroyed, and when the body reaches the second goblin in the same list the shot already reads as gone, so it takes 0. Row 5 is the lifetime: **Timer Elapsed** (`shotTimer` at least 2) → **Destroy Object In Variable** on `shot`. The fire row itself is Key Pressed Z → Spawn Object Into Variable (fireball at the hero's edge, into `shot`) → Reset Timer `shotTimer`, gated on **Attack Ready** if you want the canned cooldown, or on your own timer the way the melee row does it.

**What the rebuilds do not carry over.** Attack Ready reads the combat module's cooldowns, which the rebuilds never touch — a rebuild paces itself with its own timer, as above. The growth and scaling damage bonuses do not ride along either: Damage Object names the victim, not an attacker, so read the bonus with Read Damage Bonus and add it in the amount expression (`10 + dmgBonus`). One shot at a time: firing again while a shot still flies overwrites `shot`, and the first shot is stranded — the flight row follows the newest one. Keeping a list of live shots is object references inside structures: store each shot's handle in a list with Store Object In Structure and read it back with Read Object From Structure. The rebuilds are verified in the export tests (Phase CO): the melee chain hits the goblin in front, spares the one behind and the one out of range; the shot chain flies, hits the first of two stacked goblins once, spares the second, and dies on its timer with nothing to hit.

## Moving platforms

Now the ground itself moves. A **moving platform** slides between two points and carries anything standing on it, so the hero rides a lift across a pit or a conveyor across a gap instead of jumping it. Turn any object into one from the Inspector **Platform** section: tick **Moving platform**, set **Point 1** and **Point 2** (absolute world positions — the platform's top-left corner travels between them), pick a **Speed** in pixels per second (60 is a gentle ride, 200 is a brisk lift), and choose a **Mode** — Ping-pong goes there and back, Loop jumps back to the first point and starts over. Turning the platform on with no path yet seeds one from where it stands: 200 pixels to the right and back. A parked platform (Speed 0) stays a floor that never moves.

**Set Platform Path** does the same thing while the game runs: give it the object, two points, a speed, and a mode, and the object starts moving at once — a switch that starts a lift is one block. The first point is where the platform jumps to immediately, so set the points to where it already is to start from there. **Standing On Platform** is true while an object stands on a moving platform — the ride is on — so play a platform hum, or warn the player before a crumbling platform gives way. Both read every frame, even while paused.

**One-way platforms** are ledges you jump up through and land on from above. Tick **One-way platform** in the Platform section, or in the Inspector **Collision** section (the two boxes are the same flag), or run **Set One-Way Platform** while the game runs — it works on any object, platform or plain floor. A hero rising through one never counts as standing on it, so jumping up through a one-way platform never grants a free ground jump, and landing on it from above refills the jumps like any other floor. **Standing On One-Way** is true while an object stands on a one-way floor, platform or plain.

**Crumbling platforms** fall away after the player stands on them. Set **Crumble after** in the Platform section, or **Set Crumble Time** while the game runs — 2 seconds is a fair crossing window, 0 means it never crumbles. Once a rider stands on the platform the timer starts and runs to the end even if the rider steps off; when it expires the platform stops being solid and vanishes, so the rider drops through. A parked floor can crumble too — it never moves, it just falls away underfoot.

A few honest limits. Platforms move on straight legs between their points — no curves. The carry is direct: only objects standing on the platform itself ride it, so a rider standing on another rider is carried by physics, not by the platform. A platform moves by direct position steps, like a dash, so keep its path clear of walls — it can sit inside a thin wall for a frame before the next physics step pushes it back out. One-way platforms block from above only, never from the side or below. A crumbled platform stays gone until the scene reloads. Platform state is transient run state: a fresh scene starts with every platform back at its first waypoint and no crumble timer running, and nothing travels in save slots. There is no script-API surface for platforms yet — use the blocks.

## Tilemaps

A **tilemap** is the classic way to build platformer ground, RPG towns, and roguelike dungeons: a grid of square tiles painted from a tileset image, where the solid tiles stop the player automatically. Create one from the Create palette (**Tilemap**) or the Add Entity dropdown — it starts as a 10x10 grid of 32px tiles.

Select the tilemap to open its inspector section:

- **Tileset image**: pick an image asset to paint with, or leave it on None and tiles draw as colored squares (handy for prototyping). The tileset is sliced on a grid of tile-size squares, so tile 0 is the top-left square, tile 1 the next one, and so on; **Tileset columns** tells the engine how many tiles each row of your image holds.
- **Tile size** and **Map size**: tile size in pixels (8-256), map width and height in tiles (up to 200x200). Resizing keeps the tiles that still fit.
- **Tiles strip**: click a tile to pick it as your brush; right-click a tile to toggle whether it is **solid** (solid tiles get an amber S badge and are listed under the strip). Tile 0 starts solid, so the first thing you paint is ground.
- **Brush / Eraser / Mode**: the brush paints, the eraser clears, and Mode toggles between **Paint** (click and drag on the map to paint) and **Move** (drag the whole tilemap around the scene). Right-click a cell on the map to erase it.
- **Edit as text**: type the map as rows of characters — `0`-`9` and `a`-`z` pick tiles 0-35, `#@$%&` pick tiles 36-40, `.` or space is empty — then Apply. Great for sketching a level fast or pasting one from a friend.

Collision is automatic: any physics-enabled object bumps into, lands on, and slides along the map's solid tiles — no blocks needed. Tilemaps never collide as whole objects (that would make the entire map rectangle solid); only the solid tiles do. Three **Tilemap** blocks cover gameplay logic: **Set Tile** paints or clears a single cell while the game runs (build bridges, crumble floors, open doors — use -1 to clear), **Tile Solid At** asks whether the tile at a world position is solid, and **Standing On Tile** is the tile-aware grounded check for jump logic (true when the object's feet rest on a solid tile). Everything — painting, collision, and the blocks — works identically in the preview and in exported games.

## Physics upgrade

Real engines do not give every object the same box collider. HydraScript now has five collider upgrades, all set in the Inspector under **Collision** on any object (tilemaps collide per-tile, so they skip this section):

- **Shape**: Box or Circle. The circle is centered on the hitbox with a radius of half the smaller side — perfect for balls, coins, and round enemies. Boxes keep the exact behavior they always had.
- **Collider**: **Solid** blocks movement (walls, ground, platforms). **Trigger** never blocks anything — it only reports touches. Mark a coin pickup or a doorway as a trigger and use **Trigger Enter** / **Trigger Exit** to react the first frame something walks in (or out). Triggers fire once per entry, not every frame.
- **One-way platform**: land on it from above, jump straight up through it from below. The classic platformer ledge, with no extra blocks.
- **Layer** (0-7) and **Collides with**: collision layers decide which objects can touch each other at all. Two objects interact only when each one's "collides with" includes the other's layer. Leave everything checked for the classic behavior — every object touches every other object. Uncheck a layer to make ghosts that pass through walls, or to keep enemies on one team from colliding with each other.

Five **Collision** blocks round out the pillar: **Trigger Enter** and **Trigger Exit** (edge-triggered — they fire once, on the frame a touch starts or ends), **Raycast Hit** (shoots an invisible line from one point to another and reports the closest collider it hits — line of sight, laser guns, "is there ground below me?"), **Objects Overlapping** (true when any collider overlaps a circle you describe with a center and radius — explosion blast radius, pickup magnets), and **Set Collision Layer** (moves an object to a new layer at runtime — a ghost power-up that stops colliding with walls). All of it works identically in the preview and in exported games.

Four more **Collision** blocks answer object-to-object spatial questions, the queries enemy AI and aiming systems are built from:

- **Angle Between**: the angle in degrees from one object to another, compared with at least / at most / equals / not equals / greater than / less than. 0 means directly right, 90 directly down, -90 directly up. A turret that fires when the angle to the player is within a cone is just Angle Between → Shoot.
- **Line of Sight**: true when no collider blocks the straight line between two objects — the classic "can the guard see me?" check. The two objects' own colliders are ignored; anything else on the layers you picked blocks the view. Like Raycast Hit, it reports the freeze while the game is paused.
- **Distance To Nearest**: the distance from an object to the closest object in a named group, compared against a value. Enemy aggro ranges, magnet pickups, and "nearest coin" highlights all start here. When no object in the group exists, it stays quiet.
- **Moving Towards**: true when an object is actually moving toward another — chasing enemies, homing missiles. A stationary object never counts.

All four are state reads, so they are true every frame while the state holds (you can flip any of them to fire once on the properties panel). They work the same in the preview and in exported games.

## Menus and HUD

Title screens, pause menus, and score bars are built from three widget objects, found in the Scene tab under **Create**:

- **Button**: a clickable button with a real background. It shows your hover and pressed colors automatically (set them in the Inspector under **Button style**), and it fires the **Object Clicked** and **Mouse Over** blocks so logic can respond.
- **Label**: that is just a Text object (fixed to the screen by default) — use it for titles, scores, and hints.
- **Panel**: a rounded-rect backdrop that frames a menu. Give it a border color for a title-card look.

Two layout tools keep menus glued to the screen no matter where the camera goes:

- **Anchor to screen** (Inspector, **Menus & HUD**): pin the widget to a corner, edge, or center of the screen. X and Y become the offset from that point in pixels. Example: anchor a button **Top right** with X -20 and Y 20, and it sits 20 pixels in from the top-right corner on any window size, in the preview and in exported games.
- **HUD layer**: tick **HUD layer (always on top)** and the widget draws above everything else, ignoring the camera. Score bars, pause menus, and dialog boxes live here.

A typical main menu: one Panel anchored to **Center**, a Text title pinned near the top of it, and two Buttons (Play, How to Play) anchored under the title. Wire **Object Clicked** on the Play button to **Switch Scene**. Anchored widgets show a small badge in the scene editor (for example "Top right · HUD") so you can see the layout while editing.

## Scene management

Six **Scene** blocks cover moving between scenes: **Restart Scene**, **Go To Next Scene**, **Go To Previous Scene** (wrapping around the scene list), and the push/pop pair. **Push Scene** switches to the scene you pick but remembers where you came from, so **Pop Scene** returns to it — build pause menus, settings screens, and pop-up dialogs as ordinary scenes and let Pop Scene find the way back, no matter which level opened them. Up to 16 scenes can be stacked; a 17th push is ignored. Every scene change happens at the end of the frame, so the rest of the current event still runs against the old scene. One honest limit: only the scene id is remembered, so a scene's objects re-instantiate fresh when you come back — game variables (which are global) are what carry state across. **Set Scene Background** recolors the current scene behind everything, instantly; a scene background image, when one is set, still draws on top of the color. Everything works the same in the preview and in exported games.

## Camera

Sixteen **Camera** blocks steer what the player sees. The camera shows a window onto the world: its position is the world point at the top-left of the screen, and it can never scroll past the world's edges.
- **Move Camera** puts the camera's top-left at an X/Y you give (try `player.posX - 400` to snap it near the player). It also clears any follow.
- **Follow Object** keeps the camera centered on an object every frame, with an optional offset (the classic platformer camera). **Center Camera On** does the same thing exactly once, without starting a follow.
- **Stop Camera Follow** leaves the camera where it is; **Reset Camera** stops the follow, puts zoom back to 1, and returns to the top-left of the world.
- **Set Camera Zoom** scales the whole world render: 1 is normal, 2 zooms in (everything looks twice as big), 0.5 zooms out to show more of the level. Zoom clamps to 0.25-4. Clicking still hits the right objects while zoomed, and HUD and pinned widgets stay put — only the world scales.
- **Camera Position** is a condition that reads the live camera: Camera X, Camera Y, or Zoom compared against a value. Use it to trigger things when the camera reaches somewhere ("Camera X at least 1200" starts the boss music).
- **Screen Shake** jolts the view for impact, and **Screen Flash** washes the whole screen a color that fades out — white for a pickup or scene change, red for taking damage (both have one-click presets in Game Flow Presets). A flash draws above the HUD and freezes while the game is paused, so it never fights the pause menu.

**Camera feel: smoothing, deadzone, bounds.** A camera that snaps to the player every frame feels stiff, and one that can wander past the level edge shows the void. Each scene has its own feel settings in Scene Settings, and four blocks change them while the game runs:
- **Set Camera Smoothing** (0 to 0.95) decides how gently the camera chases the followed object. 0 snaps at once, the old behavior; 0.5 glides halfway to the target each frame; 0.9 is a slow cinematic drift. Smoothing follows the time scale, so a smoothed follow slows down with the world in slow motion.
- **Set Camera Deadzone** sets a width x height rectangle (world pixels) around the center of the screen. While the followed object stays inside it the camera does not move at all, so small hops and idle sways never shake the view; when the object steps out, the camera moves just enough to bring it back to the edge. 0 x 0 turns the deadzone off.
- **Set Camera Bounds** sets a world rectangle the camera view stays inside — draw it exactly around a room and the camera never shows past the walls. **Clear Camera Bounds** removes the bounds and the view goes back to staying inside the scene edges. A bounds rectangle with Min above Max warns and leaves the old bounds alone.
- **Camera Following** is a condition that is true while the camera is following an object; invert it to detect that the camera is free.

The feel is per scene: switching scenes loads the new scene's smoothing, deadzone, and bounds, so a block that changes them in one level never leaks into the next. **Reset Camera** restores the scene's feel along with the position, zoom, and follow. Honest limits: the deadzone is a centered rectangle only (no look-ahead in the direction of movement), smoothing is one number for both axes, and bounds are one rectangle per scene (change them mid-level with the Set Camera Bounds block).

**Parallax backgrounds: depth without a 3D scene.** A flat scene looks flat because everything moves with the camera at the same speed. Give a decoration layer a parallax factor and it scrolls at its own speed: a sky at 0 never scrolls at all, hills at 0.5 drift at half speed, a foreground bush at 1.5 rushes past. Set the factors in the Inspector **Parallax** section on any 2D object (X and Y are independent, 0 to 2, 1 is world speed), or change them while the game runs with the **Set Parallax** block; the **Parallax Factor** condition reads them back. The classic setup is three wide sprites stacked behind the playfield: sky 0, hills 0.5, trees 0.75. Parallax is drawing only — physics, collision, and the object's world position never move, so keep it on decoration layers and not on anything the player collides with. Clicks and button hover follow the drawn position, so a parallax button still clicks where it shows. Honest limits: 2D objects only (3D kinds and lights ignore it), and there is no repeating or tiled fill — a layer is a wide sprite you place yourself.

The camera follows and zooms identically in the preview and in exported games, and the current zoom is readable in expressions as `cameraZoom`.

## Variables, arrays, and structures

Every game variable can hold a plain value (a number, text, true/false), a **list** (an ordered set of items, also called an array), or a **structure** (a set of named fields, like a dictionary). The **Variables** palette blocks create the container on first write: if a variable held a number and a list block writes to it, it becomes a list (the old value is replaced, so pick a fresh variable name for lists). Conditions never create variables; they see a missing variable as an empty list or structure.

List indexes start at 0, and -1 means the last item. Reading past the end gives 0, never an error. **Set Array Item** grows the list with 0s when the index is past the end, up to 10,000 items.

- **Push To Array** adds a value to the end; **Pop From Array** removes the last item and can hand it to another variable. **Set Array Item** replaces by index, **Get Array Item** copies an item into another variable, **Insert Into Array** slides items right to make room, **Remove Array Item** deletes by index, **Remove Array Value** deletes the first item equal to the value, **Clear Array** empties the list.
- **Sort Array** orders the list (numbers low to high or high to low, text A to Z or Z to A); **Shuffle Array** randomizes it (the card-deck shuffle). **Array Total** computes the sum, average, minimum, or maximum into a variable. **Join Array To Text** glues the items into one text with your separator, ready to show with Set Text.
- **Array Length** is a condition comparing the item count ("at least 3 coins collected"); **Array Contains** asks whether the list holds an exact value, and inverts cleanly ("does NOT have the key yet").
- **Set Structure Field** writes a named field (`player` / `gold` = 50); **Get Structure Field** copies a field into another variable; **Remove Structure Field** deletes one; **Clear Structure** empties all fields; **List Structure Keys** stores the field names as a new list. **Structure Has Field** is the condition.
- **Variable To JSON** turns any variable into JSON text; **Variable From JSON** rebuilds it (invalid JSON warns and leaves the variable unchanged). Use the pair to snapshot complex state.
- **Nested paths** reach several levels down in one block. **Get Nested Value** reads `party[0].hp` (the hp field of the first dictionary in the party list) or `player.stats.hp` (a field of a field) into another variable; a missing step reads as 0. **Set Nested Value** writes `party[0].hp = 10`, building the lists and structures it needs on the way down, so a party list of member dictionaries grows one path write at a time. A path is field names joined by dots with `[n]` index steps (`[0].name` reads from a list root, `-1` counts from the end); a blank or malformed path warns and holds. The manual way still works: Get Array Item into a temp variable, Set Structure Field on it, Set Array Item back means the same thing. Objects travel the same paths: **Store Object In Structure** writes the object a scoped variable holds at a path (`squad[0]`, `party.leader`), building the containers on the way down, and **Read Object From Structure** reads it back into a scoped variable, so a party list can hold live goblins and each member's X, health, or alive flag reads back with Read Object Property. A missing step, or a value that is not an object, clears the variable, so a later Is alive read is 0. The manual way still works for objects too: Read Scoped Variable into an ordinary variable, Set Nested Value with Copy of another variable, then Get Nested Value and Read Object Property to read it back.

Every value field has a **Value is** picker: **Number (expression)** evaluates like any expression field, **Text** takes the text literally (an item named "sword", not a variable called sword), **True**/**False**, and **Copy of another variable**, which deep-copies — pushing a structure into a list stores a snapshot, so later edits to the structure never change the stored copy. To use a list item or structure field inside a formula, copy it into a plain variable first with **Get Array Item** or **Get Structure Field**; expressions read plain variables. Everything behaves identically in the preview and in exported games, and lists and structures save and load through the save-slot blocks like any other variable.

**Random numbers and tidy math.** Dice rolls and luck need whole numbers: **Random Integer** stores a whole number between Min and Max, inclusive on both ends (roll = 1..6 for a die; Min and Max swap automatically when Min is bigger). **Random Pick** copies a random item out of a list variable (a random card from a deck; 0 when the list is empty or missing). Two helpers keep numbers clean without writing formulas: **Clamp Number** forces a variable into a range (health that cannot pass 100 or drop below 0), and **Round Number** rounds a variable to a whole number, down, up, or to 1-2 decimal places for tidy score displays. **Number In Range** is the condition form: true while a value sits between Minimum and Maximum, inclusive (a state read, so it holds true every frame the value is in range and inverts cleanly for "outside the zone"). Bad numbers and blank names warn instead of silently misbehaving.

**Typing a value into the game.** A player can type a number with only blocks: a digit key (just pressed) appends its digit to a text object with **Append Text**, and **Read Text Into Variable** reads the text back into an ordinary variable — Number mode parses it, Text mode keeps it as text. Then **Set Scoped Variable** with "Copy of another variable" writes it into the scoped variable. The **Variable Inspector** template (New Project) is the acceptance game for the whole core-engine track: it lists the game's variables on screen (a global score, per-scene coins, one goblin's HP, a text name), each with − / + buttons that edit it, a type-a-number row with a Set button, and live values that refresh every frame — while the coin and goblin gameplay keeps changing the same values from play, so the inspector watches change from both sides. A bad Set warns and leaves the score at its last good value (the first bad Set reads the missing value as 0). One honest limit: the inspector's rows are built for the game's known variables — there is no block that lists every variable by itself, so a variable added in the manager needs its own row.

## Logic: conditions and actions

Game logic is made of **events**. Each event is one **condition** block plus the **action** blocks that run when it is true.

On the grid, place a condition block, then put actions next to it: in the same highlighted group, directly adjacent, or to its right on the same row. Example: a **Keyboard** block (ArrowRight, held down) with an **Apply Force** block next to it (player, X = 5) makes the player move right.

Most conditions have an **Invert** toggle (NOT this condition).

Two scopes: the **Global** grid runs in every scene; each scene also has its own grid that runs only there. Switch scopes with the tabs above the grid.

When a scope has no blocks yet, a hint bar appears over the grid with an **Add your first block** button that opens the block picker. Dismiss it with the X; it comes back when you switch to another empty scope.

Hover any block in the palette to see what it does in one plain sentence, with a tiny example where one helps. The same text shows in the block picker detail pane, and hovering a block already on the grid shows its tooltip again, so you never have to guess what a block you placed last week was for.

## Variables and expressions

**Set Variable** creates or changes a number or text value, like `score`. **Variable Check** tests it (score >= 10). **On Game Start** plus **Set Variable** is the standard setup event.

Many fields accept **expressions**, not just numbers. Examples:

- `score + 10`
- `player.posX - 400` (camera follows the player)
- `Math.floor(Math.random() * 690) + 40` (random spawn)
- `enemy.posX + 10`

You can read any object's properties: `name.posX`, `name.posY`, `name.width`, `name.height`. If an expression mentions something that does not exist, the game warns you in the diagnostics panel instead of silently doing the wrong thing.

## Text scripting

The **Code** category has two blocks for writing JavaScript directly: **Run Script** (an action that runs your code) and **Script Check** (a condition that is true when your code reads as true). They exist for logic that would take twenty blocks to build visually. Everything the scripts can do is also doable with blocks, so scripts are a shortcut, never a requirement.

Your code gets one object, `hs`, with the whole documented API:

| Call | What it does |
|---|---|
| `hs.get('score')` / `hs.set('score', 5)` / `hs.has('score')` | Read, write, and check game variables |
| `hs.obj('hero')` / `hs.objs('enemy')` / `hs.count('coin')` | Get wrapped objects by name (first / all / how many) |
| `hero.x`, `hero.y`, `hero.cx`, `hero.cy`, `hero.w`, `hero.h` | Position, center, and size (x/y are the top-left corner) |
| `hero.move(dx, dy)` / `hero.teleport(x, y)` | Shift or place the object |
| `hero.setText('hi')` / `hero.text` | Change or read a text object's text |
| `hero.show()` / `hero.hide()` / `hero.visible` | Show, hide, or check visibility |
| `hero.setColor('#ff0000')` / `hero.setOpacity(0.5)` / `hero.setRotation(45)` | Change how it looks |
| `hero.destroy()` | Destroy the object at the end of the frame |
| `hs.dist(a, b)` | Center-to-center distance between two objects (names or wrapped objects) |
| `hs.input('Jump')` | `{ held, pressed, released }` for a named input action from the Inputs tab |
| `hs.elapsed('timer')` / `hs.startTimer('timer')` / `hs.stopTimer('timer')` / `hs.resetTimer('timer')` | Named timers; elapsed reads 0 for a timer that was never started |
| `hs.play('coin')` / `hs.play('theme', { bus: 'music', volume: 0.5, pitch: 1.2 })` | Play an uploaded audio asset (or the built-in tone when no asset matches) |
| `hs.stopMusic()` / `hs.setBusVolume('music', 0.5)` / `hs.setBusMuted('sfx', true)` / `hs.musicPlaying()` | Music and bus control |
| `hs.switchScene('Level 2')` / `hs.scene()` | Switch scenes by name (deferred like the block) / read the current scene name |
| `hs.camera.x` / `hs.camera.y` / `hs.camera.zoom` | Read the camera |
| `hs.camera.moveTo(x, y)` / `hs.camera.setZoom(1.5)` | Move the camera, set the zoom |
| `hs.camera.centerOn('hero')` / `hs.camera.follow('hero', 0, -40)` / `hs.camera.stopFollow()` / `hs.camera.reset()` | Camera recipes from code |
| `hs.burst('Explosion', x, y)` / `hs.startEmitter('fire1', 'Fire', x, y)` / `hs.stopEmitter('fire1')` / `hs.clearParticles()` | Particles, using the same preset names as the blocks |
| `hs.saveGame('Slot 1')` / `hs.loadGame('Slot 1')` / `hs.deleteSave('Slot 1')` / `hs.saveExists('Slot 1')` | Save slots |
| `hs.pause()` / `hs.resume()` / `hs.isPaused()` | Pause control; scripts keep running while paused |
| `hs.showProfiler()` / `hs.hideProfiler()` / `hs.profilerVisible()` | The profiling overlay |
| `hs.setTile('map', col, row, 3)` / `hs.tileSolidAt('map', px, py)` | Paint tilemap cells and test solid tiles |
| `hs.rand(1, 10)` / `hs.randInt(1, 6)` / `hs.clamp(v, 0, 100)` / `hs.round(v)` | Small math helpers |
| `hs.dt` | Seconds since the last frame, for frame-rate-independent movement |
| `hs.log('hello')` | Print to the browser console while debugging |

Three recipes to get started:

1. **Chase the player.** Run Script on Every Frame: `var p = hs.obj('player'), e = hs.obj('enemy'); if (p && e) { var dx = p.cx - e.cx, d = Math.abs(dx); if (d > 4) e.move(Math.sign(dx) * 120 * hs.dt, 0); }`
2. **Score popup.** Script Check with `hs.get('score') >= 100`, chained to Show Object and Play Sound blocks.
3. **Debug key.** Key Just Pressed (F3) with Run Script: `if (hs.profilerVisible()) hs.hideProfiler(); else hs.showProfiler();`

Honest limits: a `while (true)` loop freezes the game the same way it would in any JavaScript, so keep loops short. A script with an error warns in the diagnostics panel (preview) or the console plus HUD badge (exports) and the game keeps running; a Script Check with an error reads as false. Script code is real JavaScript, so only open projects with scripts from people you trust (see "Staying safe with shared project files").

## Save slots

Variables reset every time the game restarts — unless you save them. **Save Game** writes ALL of your variables into a named save slot (think of it as a memory card in your browser); **Load Game** restores them; **Delete Save** clears a slot; and the **Save Slot Exists** condition tells you whether a slot holds a saved game.

Typical setup for a game with level unlocks and a high score:

- Title screen: **Save Slot Exists** "Slot 1" → show a Continue button. Invert it to show a New Game button when there is no save.
- Game Start: **Load Game** "Slot 1" — the player picks up where they left off.
- Level complete: Set Variable `levelUnlocked` to the next level, Set Variable `bestScore` if the score beat it, then **Save Game** "Slot 1".
- New Game button (Object Clicked): **Delete Save** "Slot 1", then reset the variables and start over.

Saves work in the editor preview and in exported games, and the same slot is shared between them — so you can test a save in the preview and continue it in the exported game. If a save is ever corrupted, the game treats the slot as empty instead of crashing.

## Pause and resume

**Pause Game** freezes the game world: objects stop moving, animations and tweens stop, the camera stops, and timers hold their place. The game keeps drawing every frame and buttons keep working, so a pause menu built from panels and buttons stays alive and clickable. **Resume Game** unfreezes exactly where you paused; **Toggle Pause** flips between the two with one block (handy for a pause key); and the **Game Paused** condition tells you whether the game is paused right now.

While paused, your logic still runs — only the world freezes. That is what makes the pause menu itself plain blocks:

- Key Just Pressed (P or Escape) → **Pause Game**
- **Game Paused** → Show your pause panel and Resume button
- Object Clicked (Resume button) → **Resume Game**, then Hide the pause panel and button

Two details worth knowing: Collision, Overlap/Touch, On Floor, and On Screen Edge do not fire while paused (the world is frozen, so contacts would be stale), and On Timer does not tick — it resumes where it left off. If you want your own gameplay actions frozen too, gate them with **Game Paused** inverted, for example "Game Paused (inverted) + Collision → lives − 1". Switching scenes always unpauses, so a "quit to title" button just works.

**Reading a timer.** On Timer fires every N seconds, but sometimes you want to ask "how long has it been?" instead. **Timer Elapsed** is a condition that compares a named timer's elapsed seconds against a number you enter (at least, at most, exactly, and the rest), and **Read Timer** copies the elapsed seconds into a game variable so you can show a countdown or do math with it. Both hold their value while the game is paused, and both read 0 for a timer that was never started. A classic pattern: Reset / Pause Timer ("wave") when a wave starts, Timer Elapsed ("wave" >= 30) to spawn the boss, and Read Timer ("wave" into "waveTime") feeding a Set Text block that shows "Wave ends in ..." on the HUD.

## Profiling overlay

When a scene feels slow, the **profiling overlay** tells you why. It is a small panel that shows FPS (frames per second), frame time in milliseconds, and how many sprites, 3D triangles, particles, and objects the game drew this frame. The fastest way to see it: open the **Preview** tab and click the gauge button in the preview toolbar — no blocks needed. In an exported game, use the **Game Flow** blocks instead: **Show Profiler**, **Hide Profiler**, and **Toggle Profiler** (pair it with Key Just Pressed so F3 flips the overlay on and off). The **Profiler Visible** condition tells you whether the overlay is on screen.

Two details worth knowing: the FPS number is a rolling average over the last 60 frames, so one hiccup barely moves it — a steadily low number means the scene is genuinely heavy. And the counts are per-frame draw counts, not totals in the project: a high sprite count usually means many objects on screen at once, while a high 3D-triangle count means heavy geometry. The overlay is a debugging tool, so hide it before you share the game.

## Flow tracer

When a block should fire but nothing happens (or the wrong thing happens), the **flow tracer** shows you exactly what ran, in order. Open the **Preview** tab and click the route button in the preview toolbar — no blocks needed. While tracing is on, three things happen: the **Trace panel** in the bottom-left of the preview lists every firing block as one line per event (`frame 12 · global cell 0 · trigger always`, then the chained action right after it), grid cells that fired in the last 30 frames get a cyan ring on the logic grid, and the button stays lit so you can see tracing is on. Click the button again to stop; the **Clear** button in the panel empties the feed without stopping.

Two details worth knowing: the panel keeps the 200 most recent events, so a block that fires every frame (like Always) fills it fast — that is the point, it shows you the real firing rate. And tracing is a debugging tool, not game state: it starts off on every preview run, it is never saved into your project, and it survives scene switches within a run. In an exported game, add `?hydraTrace=1` to the URL to turn tracing on; the event ring is then available as `window.__hydraTrace` in the browser devtools console.

## Preview and diagnostics

The **Preview** tab runs the game. If something is wrong, check the **diagnostics** panel: it reports unknown blocks, bad expressions, and dangling references (for example a block pointing at an object you renamed). Fix the warning, preview again. If the diagnostics are clean but the logic still misbehaves, turn on the **flow tracer** above and watch which blocks actually fire.

**Block validation:** the editor also checks your logic without running it. Every time you open a project, edit the grid, or delete an object or a scene, it scans every block in the Global grid and every scene grid and reports three kinds of problems in the same diagnostics panel: a block naming an object that is not in that scene ("Block 1 (Move Object) in Level 1 names object "ghost", which is not in this scene"), a block switching to a scene that does not exist, and an expression that will not run ("Block 3 (Set Variable) in Level 1 has an expression that will not run: "score +""). A block that only reads a variable name is fine even before the variable exists — variables are created at runtime, so the check is about syntax, not about names it has not seen yet. A Global-grid block is checked against every scene's objects, since Global logic runs in all of them; a scene-grid block only sees its own scene. Fix the block and the warning clears on its own — no reload, no preview needed. The check caps at 100 findings so one broken import cannot flood the panel.

**Device frames:** the preview toolbar has a device selector (Desktop, Phone portrait/landscape, Tablet portrait) that wraps the game in a phone or tablet bezel, so you can see how the game fits on a smaller screen before exporting. The game is letterboxed inside the frame: it keeps its own aspect ratio at one uniform scale, the way a real phone letterboxes a game instead of stretching it, so circles stay circles and a landscape game on a portrait phone shows as a wide strip with empty bezel above and below it. One honest limit: the frame only changes how big the game is *shown* — the game itself still renders at the scene's viewport size, so a frame is a scaling preview, not a re-layout. If the preview pane is smaller than the device, the frame scales down to fit. The FPS counter lives in the **profiling overlay** above: click the gauge button in the same toolbar.

**Status bar:** the thin bar at the very bottom of the editor always shows the current scene name, how many objects the current scene has, the live preview FPS, and how many diagnostics are open. FPS reads a dash while no preview is running and a live number while the Preview tab plays; the diagnostics count turns amber when something is open, and clicking it opens the diagnostics panel.

Common gotchas:

- Logic is in the wrong scope (scene grid vs Global).
- An action is not next to its condition, so it never runs.
- A block references an object name that no longer exists.
- `switchScene` happens at the end of the frame, so actions after it in the same event still see the old scene.

## Export a playable game

Click **Export Game** to open the export dialog. Pick a target:

- **Single HTML file.** One file with your game and the whole engine inside it. No internet needed to play it. Put it on any static host (or just double-click it) and share the file.
- **Website ZIP (itch.io).** A ZIP with `index.html` plus an `assets/` folder holding your images and audio as separate files, all linked with relative paths. On itch.io: create a project, upload the ZIP, set Kind of project to HTML, tick "This file will be played in the browser", set the viewport to your scene size, then publish.
- **Installable app (PWA).** Everything in the Website ZIP, plus a web manifest, an offline service worker, and 192px + 512px icons drawn from your game's name. Unzip it, host the folder over HTTPS (itch.io, GitHub Pages, and Netlify Drop all work), and open the URL once: the browser offers Install, and the game plays offline after the first visit.
- **Desktop app (Electron).** A complete Electron + electron-builder project that becomes real Windows, macOS, and Linux installers: `package.json`, a `main.js` window shell sized to your scene, a 512px icon drawn from your game's name, your game as `game/index.html` + `assets/`, and a README with the exact commands. Unzip it, run `npm install` (needs Node.js), then `npm start` to play or `npm run dist` for the installers. Building the binary always runs on your machine; the engine never signs or notarizes (unsigned builds play fine but show the usual unknown-publisher warning until you sign with your own certificate), and branded Windows/macOS icons are your step — convert `build/icon.png` to `icon.ico` / `icon.icns` and electron-builder picks them up automatically.
- **Android app (Capacitor).** A complete Capacitor project that becomes a real Android APK: `package.json` (Capacitor deps), `capacitor.config.json` (your app id, app name, `webDir: "www"`), your game as `www/index.html` + `assets/`, a 1024px icon and splash drawn from your game's name, and a README with the exact commands. Unzip it, run `npm install`, then `npx cap add android` and `npx cap sync`, then `npm run build:apk` for a debug APK you can install on your phone. The native project generates on your machine via `npx cap add`; a Play Store release needs your own signing key.
- **iOS app (Capacitor).** The same complete Capacitor project as the Android card, with iOS guidance instead. On a Mac, run `npm install`, then `npx cap add ios` and `npx cap sync`, then open `ios/` in Xcode and build. An iOS binary requires macOS + Xcode — the engine produces the full iOS project, but Apple builds the binary — and an App Store release needs your own Apple Developer account and signing.

Each card in the dialog lists exactly what the engine generated, what you do next, and what cannot be automated (uploading to your itch.io account and hosting the PWA folder need your login, so those steps are always yours). Every card also carries an honest capability line — what that target plays like and what it cannot do — and the desktop and mobile cards have click-to-copy command chips, so the exact terminal commands move to your clipboard with one click.

Exported games keep working even if the editor changes later, because the engine is embedded in the file.

## 3D basics

HydraScript renders real 3D with a built-in perspective camera — no plugins, no WebGL code to write, and exported games stay self-contained. 3D is **per scene**: open Scene Settings and flip **Render Mode** from 2D (classic) to 3D (perspective). The preview and exported games then draw that scene in true 3D.

**Four 3D primitives** live in the Create palette: **Box 3D**, **Sphere 3D**, **Plane 3D**, and **Cylinder 3D** — plus **Model 3D** for your own uploaded models. Place one and the scene editor shows a small live 3D thumbnail (with a 3D badge) so you can see what you are placing; drag moves it on the X/Y plane like any 2D object, and the Inspector's **3D Transform** section sets the rest: **Z (toward viewer)** for depth (0 is the screen plane, positive comes closer), **Depth** for the size along Z, and **Rot X / Rot Y / Rot Z** in degrees, spinning about the object's center.

For a 3D scene, the scene toolbar grows a **Layout / 3D view** toggle. Layout is the place-and-drag editor you already know; **3D view** renders the true perspective picture — the same engine Preview and exported games use, with the scene's actual camera — right in the editor. Frame that camera in Scene Settings: **3D Camera Position**, **3D Camera Look-At**, and **FOV** (field of view), with a **Reset to frame scene** button that restores the default whole-scene framing.

The coordinates follow your 2D intuition on purpose: X grows right, Y grows DOWN like the 2D canvas, and Z grows toward the viewer. All seventeen **3D** blocks work on the object's **center** (X + Width/2, Y + Height/2, Z):

- **Move 3D** nudges the object by dX/dY/dZ — chain it after an **Every Frame** block for smooth motion.
- **Set 3D Position** teleports the center to an exact X/Y/Z.
- **Set 3D Rotation** sets the absolute rotation in degrees (Rot Y spins like a turntable); **Rotate 3D** adds degrees, so Every Frame + Rotate 3D (Rot Y 2) is the classic showcase spin.
- **Set 3D Camera** moves the camera and aims it at a look-at point — the default camera already frames the whole scene, so reach for this for dramatic angles or fly-bys. It also ends any camera follow.
- **Follow 3D Object** is the third-person chase camera: every frame the camera rides the object's center plus your offset, always looking at it. Offset X moves the camera right, Offset Y down (negative = above), Offset Z toward the viewer — try (0, -60, 280) for a classic behind-and-above view. **Stop 3D Camera Follow** ends it and the camera holds still.
- **3D Distance** is a condition comparing the center-to-center 3D distance between two objects — the 3D version of Distance Check, perfect for 3D pickups and proximity triggers.
- **Set 3D Gravity** gives a 3D object gravity so it falls downward every frame (the 3D version of Set Gravity); **Set 3D Velocity** sets its velocity directly — a negative VY is a jump.
- **3D On Ground** is true while a 3D object rests on a solid surface (the 3D version of On Floor); **3D Collision** is true while two 3D objects' colliders touch (the 3D version of Collision).
- **Set 3D Light** changes a light while the game runs — its type, color, intensity, range, or on/off (see 3D lighting below).

**3D models:** upload a `.glb` file on the **Assets** tab (it appears as a 3D Model asset; a `texture` tag marks models that carry embedded textures), create a **Model 3D** object, and pick the file in the Inspector's **Model** field — the thumbnail shows your actual model, scaled to fit the object's Width / Height / Depth box. A textured model shows its own skin automatically; **Use model texture** in the Inspector (or the **Use Model Texture** block) switches between the texture and the flat material colors. **Material color (tint)** multiplies the model's own colors: white shows them untouched, red makes the whole model glow red. The **Set Model Tint** block changes the tint while the game runs (flash red on a hit). Models render with flat shading from their material colors; glTF's Y-up is converted automatically so authored models stand upright.

A few honest limits of the 3D support so far: 3D objects ignore the 2D physics and collision system (they have their own 3D physics instead — see below), 2D click/hover blocks do not hit-test 3D objects yet, and a subtle reference grid draws on the screen plane to help you judge depth. 2D objects and HUD widgets keep working in 3D scenes — draw your menus and score bars exactly as before. 3D colliders stay axis-aligned (a spinning object's collider does not rotate with it). Models carry geometry, flat material colors, and embedded base-color textures (a texture needs a `.glb` with the image embedded — a `.gltf` that points at a separate image file renders with flat colors; no skeletal animation — a rigged character renders in its bind pose). Lights are invisible objects that shade the scene (see 3D lighting below); simple blob shadows are a per-scene switch, not real shadow mapping.

## 3D physics

3D objects can fall, land, and bump into each other — with the same vocabulary as 2D physics. Every 3D object already has the shared **Physics** panel in the Inspector (Static / Physics toggles plus Gravity, Friction, and Max Speed — one panel drives both 2D and 3D), and a new **3D Collider** section: **Collider shape** (Box or Sphere) and **Solid** (on by default; off makes the object a ghost that everything passes through).

The rules mirror 2D exactly. An object with **Physics on** and **Static off** is a dynamic — it falls under its gravity and collides. An object with **Static on** (or Physics off) is a solid obstacle — a floor, a wall. Dynamics push out of solids along the shallowest overlap and come to rest on top of them; walls stop sideways motion. A sphere collider is centered on the object with a radius of half its smallest side — great for balls and boulders.

**The 3D platformer recipe:**

1. Make a 3D scene and place a **Box 3D** named `Player` (Physics **on**, Static **off**) and a wide **Plane 3D** named `Ground` (Static **on**) below it.
2. `Scene Start` → **Set 3D Gravity** (`Player`, Gravity `0.8`). The player falls and lands on the ground — no more blocks needed for that part.
3. **Jump:** `3D On Ground` (`Player`) plus `Action Input (Jump, Just pressed)` → **Set 3D Velocity** (`Player`, VX 0, VY -8, VZ 0). The jump only fires while the player is grounded — the classic platformer move, in three blocks.
4. **Walking into walls:** a static Box 3D stops the player sideways, like a 2D wall.
5. **Pickups:** `3D Collision` (`Player`, `Coin`) → collect the coin.

Like their 2D counterparts, **3D On Ground** and **3D Collision** report the paused freeze (they do not fire while the game is paused), and both default to checking every frame while their state holds. If a 3D object never moves despite gravity, check that its Physics toggle is on — and that it is actually a 3D object, because the 2D physics system still ignores 3D objects (and the 3D system ignores 2D ones).

## 3D character controllers

There is no "FPS controller" component to drop in — and that is deliberate. An FPS camera and a third-person camera are each about six ordinary blocks you can open, change, and rebuild by hand. These are the recipes; every part is a block you already know.

**The shared idea.** A controller is three jobs: (1) read the mouse every frame, (2) turn that into a yaw (and pitch) number, (3) point the camera and move the player from those numbers. The new blocks cover the 3D-specific parts; the **Inputs tab** (named actions) covers the keys.

**Recipe 1: FPS mouse-look + WASD.**

1. Make a 3D scene (Scene Settings → Render Mode 3D) and place a **Box 3D** named `Player`.
2. On the **Inputs tab**, add four named actions — `Forward`, `Back`, `StrafeLeft`, `StrafeRight` — and bind them to W, S, A, D (click a binding to capture the key).
3. **Click to play:** put a button on a 2D menu scene (or a text object that says "Click to play"). `Object Clicked (PlayButton)` → **Capture Mouse**. Browsers only grant pointer lock from a real click, so this step is required, not optional. While captured, the cursor hides and the mouse reports movement instead of position; pressing **Esc** always releases it.
4. **Steer the yaw:** `Every Frame` → **Read Mouse Delta** (Into `mdx`, Into `mdy`) → **Set Variable** `yaw` = `yaw + mdx * 0.25` → **Set Variable** `pitch` = `pitch + mdy * 0.25`, then **Clamp Number** on `pitch` between -80 and 80 so you cannot flip upside down. Yaw 0 faces into the screen; positive yaw turns right. Pitch 0 is level; positive pitch looks down.
5. **Ride the head:** `Scene Start` (or Game Start) → **Follow 3D Object** (`Player`, offsets 0, -40, 0). The camera now sits inside the player's head every frame, always looking at the player.
6. **Aim:** `Every Frame` → **Aim 3D Camera** (Yaw `yaw`, Pitch `pitch`, Look distance 500). Unlike Set 3D Camera this never ends the follow — that is the whole trick: the follow parks the camera, the aim points it.
7. **Walk:** `Action Input (Forward, Held)` → **Move 3D Facing** (`Player`, Forward 4, Strafe 0, Yaw `yaw`). Add three more rows for Back (Forward -4), StrafeLeft (Strafe -4), and StrafeRight (Strafe 4). Forward steps toward the yaw heading, Strafe steps right — the same yaw you steer with the mouse, so movement and looking always agree.
8. **Esc menu:** `Mouse Pointer Captured` (Invert **On**) → show the pause menu and a "Click to resume" button (which runs Capture Mouse again).

**Recipe 2: third-person orbit camera.**

1. Same 3D scene and `Player` box.
2. `Every Frame` → **Read Mouse Delta** (Into `mdx`) → **Set Variable** `yaw` = `yaw + mdx * 0.3`. (No pointer lock needed — uncaptured, the delta is cursor travel, so this is drag-to-orbit.)
3. `Every Frame` → **Follow 3D Object** (`Player`, Offset X `Math.sin(yaw * Math.PI / 180) * 280`, Offset Y `-80`, Offset Z `Math.cos(yaw * Math.PI / 180) * 280`). Re-running the follow every frame with yaw-rotated offsets swings the camera around the player while it keeps looking at them — a full orbit camera from one expression.

Both recipes use only ordinary blocks: open any of them, change the numbers, and the controller changes. Nothing is hidden inside a component.

## 3D lighting

3D scenes start with a fixed studio light — fine for building, flat for atmosphere. For real mood, place **Light** objects from the Create palette (the bulb button). A light is invisible in the game: in the scene editor it shows as a bulb glyph with its type, so you can drag it into place, but Preview and exported games never draw it — it only changes how 3D objects are shaded.

**Three kinds of light**, picked in the Inspector's **Light** section:

- **Point** shines from the light's position in all directions and fades with **Range** (0 means no falloff — it reaches forever). A torch, a lamp, a muzzle flash. Z is its depth position.
- **Directional** shines everywhere from one direction, like the sun. Aim it with the light's **Rot X / Rot Y** in the 3D Transform section — no rotation reproduces the classic fixed studio light, so your scene keeps its familiar look until you turn it.
- **Ambient** has no position or direction at all — it washes the whole scene in its color. One dim ambient light is how you do night, underwater, or a red alert.

**Color** tints everything the light touches (a red point light makes a white box glow red); **Intensity** is the brightness (0 is off, 1 is normal, higher burns brighter); **Enabled** switches the light off without deleting it.

Two rules to know. First, a scene with **no lights at all** keeps the legacy fixed shading — old projects look exactly as before. Second, a scene **with lights but no Ambient light** keeps a dim built-in base light (0.25 white) so unlit faces go dark gray instead of pitch black. Adding an Ambient light replaces that base — even an intensity-0 one, which is how you ask for true darkness.

**Changing lights while the game runs** is the **Set 3D Light** block: pick the light, set its Type, Color, Intensity, Range, and On/Off. The classics:

- **Day/night cycle:** `Every Frame` → **Set 3D Light** (`Sun`, Directional, Intensity `0.5 + 0.5 * Math.sin(time * 0.1)`) — or simpler, fade an Ambient light's intensity down and watch the scene go dark.
- **Flickering torch:** `Every Frame` → **Set 3D Light** (`Torch`, Point, Intensity `1 + Math.random() * 0.3`, Range 400).
- **Muzzle flash:** on shoot, **Set 3D Light** (`Flash`, Point, bright yellow, On), then a 0.1-second timer → **Set 3D Light** (`Flash`, Off).

**Shadows** are a separate, simpler thing: Scene Settings (in a 3D scene) has a **3D Shadows** switch. On, every 3D object drops a soft dark ellipse on the ground plane below it — the **Shadow Ground Y** field sets that plane's height (blank means the bottom of the world). The ellipse fades as the object floats higher. This is a cheap blob shadow, not real shadow mapping: it cannot wrap around objects or darken walls, but it grounds floating objects beautifully for almost no cost.

A few honest limits: lights only affect 3D objects (2D sprites and HUD widgets are unlit), point-light falloff is linear (not physical inverse-square), and there is no per-light shadow casting — the blob shadows come from the scene switch, not from the lights.

## Staying safe with shared project files

Only open `.hydra` files from people and sources you trust. Expression fields in logic blocks are compiled to JavaScript when the game runs, so a project file from an untrusted source is equivalent to running their code in your browser. The full explanation is in [SECURITY.md](../SECURITY.md).

## Damaged saved data

Saved projects live in your browser's local storage, and that storage can get damaged (a crashed write, a hand-edited file, a bad import). HydraScript repairs what it can: a project whose scene list or object list came back in the wrong shape loads as the closest working version of itself, with damaged fields reset to their defaults. If the whole saved list is unreadable, the hub shows a warning banner, keeps a backup copy of the damaged data in the browser, and still loads; if only one project is too damaged to repair, it is skipped and the banner says how many were skipped, while your other projects load normally. The hub will not overwrite a damaged list until a backup copy exists. In the editor, a damaged saved project opens as a fresh project instead of a blank screen. A skipped project cannot be recovered from inside the editor, and the backup copy lives only in that browser, so if a project matters, keep a `.hydra` export of it somewhere safe.

## Accessibility

The editor is built to work without a mouse. Every button has a name a screen reader can read, every labeled control in the properties panel and scene settings is bound to its label, and the diagnostics panel announces new warnings as they appear.

**Logic grid, keyboard only:** Tab once to reach the grid, then use the arrow keys to move between cells, Home and End to jump to the ends of a row, Enter to place the selected block on the focused cell or select the block already there, and Delete to clear it. Escape moves focus back to the grid container, where the arrow keys scroll the grid instead. Each cell tells a screen reader what is on it ("Row 8, column 8: Game Start block" or "Row 8, column 8: empty cell").

**Block palette, keyboard only:** the palette is one Tab stop. Arrow keys move between blocks, Enter picks the focused block, and the search box filters the list (the Tab stop follows the first visible match). The block picker dialog opens with focus in its search box, closes with Escape, and returns focus to the button that opened it.

**Dialogs:** the Export and New Project dialogs move focus inside when they open and return it to the button that opened them when they close. Escape closes both.

**Narrow screens and motion:** below 900 pixels wide the editor stacks its side panels below the main area (inspector under the stage, properties under the grid) instead of squeezing them beside it, so nothing needs horizontal scrolling. If your system is set to reduce motion, the editor turns off its transitions and animations.

## Tips

- Start from the template closest to your idea and modify it.
- Build one event at a time and preview after each.
- Name objects before you write logic that targets them.
- Use **Comment** blocks to label what each event does. Future you will be grateful.
- Keep the Global grid for things every scene needs (score, lives); keep scene grids for level-specific logic.
