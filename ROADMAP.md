# HydraScript — ROADMAP

Prioritized, continuously updated. Completed items move to CHANGELOG.

## Design principles (Nov 2026)

1. **As powerful as the real engines, but simple.** Every capability must be usable by a non-programmer: visual blocks, sensible defaults, guided editor UI. Never ship a feature as code-only or editor-less; complex pro-engine capabilities get a simple on-ramp (presets, wizards, good defaults).
2. **Verify everything.** No feature is complete without browser tests.
3. **Backward compatible.** v3 project data keeps working.
4. **Uniqueness.** The logic grid is HydraScript's signature — do not clone competitors' signature UX (the event-sheet view was removed Nov 2026 for this reason).
5. **Primitives first, never canned game-action blocks (Ky'lin's redirect, Nov 6, 2026 — hard rule).** Real engines ship primitives (variables, functions, objects, physics queries, events), not one-block "attack" / "shoot" / "level" / "elite" systems. A one-block Melee Attack / Shoot Projectile is a scene-editor convenience, not engine power — it limits what a user can build because the mechanism is hidden inside the block. NO new canned game-action blocks. If a capability needs a friendly face, ship the primitives first and the preset second, and the preset must ship with its visible decomposition (its own block chain, documented in the user guide, rebuildable by hand). Blocks HELP, never replace and never be the only option. Existing canned blocks (Melee Attack, Shoot Projectile, leveling, scaling) stay working for backward compatibility — they are presets now, not the model for new work.
6. **The acceptance test for the core engine (Ky'lin's dream, Nov 6, 2026).** He once prototyped HydraScript itself inside GDevelop and got stuck at the variable system — it was almost impossible to build a variable system inside GDevelop. HydraScript must be powerful enough that someone could build that same prototype INSIDE HydraScript. The track that proves it is P5 below, ending in P5-9: a working variable inspector built only from HydraScript blocks inside a game.

## P4 — Engine capability pillars (pro-engine research, Nov 2026) — **PAUSED Nov 6, 2026 by Ky'lin's redirect (see P5 above): do not start batch 34 or any further Advanced batch until P5 is done. Completed P4 items stay done; the queue below is frozen.**

Research into Unreal 5, Unity 6, and Godot 4 (see the "What Makes a Game Engine Powerful" page) found one principle behind genre-agnosticism: **indirection layers** — named actions not raw keys, audio buses not per-sound volume, animation state machines not switch statements. Cheap to design early, painful to retrofit. Build those first. Browser-native advantages to protect: instant web deploy, small downloads, CPU-first effects.

**Design doctrine (Ky'lin, Nov 4):** simple on-ramps, never cages. Rival Unreal/Unity/GDevelop on power and customizability; win on simplicity. Presets, templates, and components are the *easy* way, never the *only* way: every preset must be decomposable into ordinary blocks the user could place by hand, and there must always be a manual path to build the same thing from primitives. Nothing pre-configured so tightly the user can't rebuild it their own way — never tell the user there is one way to do a thing. (Example: the Button component is one easy way to make a button; a text object plus click/hover blocks must remain a fully working alternative.)
